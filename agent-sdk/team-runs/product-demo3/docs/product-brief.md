# OwO Agent 产品简报（Product Brief）

> 面向 designer 的设计输入文档。工作区当前为空仓库，本简报定义从零搭建的单页站点：`index.html` + `styles.css`，并配套 `node:test` 测试脚本。
> 本文只定义"做什么 / 为什么 / 怎么算完成"，不提供 HTML/CSS 实现。

---

## 1. 产品定位与目标用户

### 1.1 一句话定位
OwO Agent 是一个**面向开发者的智能体 SDK 展示落地页**：用一页说清"它是什么、能做什么、怎么上手"，并把访问者推向下单/接入文档/试用。

### 1.2 目标用户（按优先级）

| 优先级 | 用户画像 | 场景 | 关键诉求 |
|---|---|---|---|
| P0 | 独立开发者 / 小团队技术负责人 | 评估是否把 Agent 能力接入自家产品 | 30 秒内判断"能不能解决我的问题"，拿到可复制的接入入口 |
| P1 | 企业技术选型人（Tech Lead / 架构师） | 对比多个 Agent 方案 | 能力边界、集成成本、可信度（是否成熟、有无案例） |
| P2 | 好奇的访客 / 社区开发者 | 从公众号、GitHub、社交渠道点进来 | 快速理解概念，找到文档与仓库入口 |

### 1.3 用户来此页面的核心问题（设计必须能回答）
1. 这是什么？（一句话能读懂）
2. 它能做什么？（3–4 个核心能力，具体而非形容词堆砌）
3. 凭什么信？（技术特征 / 案例 / 代码示例）
4. 我下一步做什么？（明确的 CTA）

## 2. 核心信息（Content Strategy）

### 2.1 主标题（Hero）
- **价值主张**：`让任何应用拥有可编排的 Agent 能力`
- **副标题**：`OwO Agent SDK — 轻量、可组合、可观测的智能体运行时，几行代码接入你的业务流程。`
- 文案准则：
  - 主标题 ≤ 20 个汉字，一眼读完。
  - 副标题 ≤ 60 个汉字，说明"是什么 + 给谁 + 带来什么"。
  - 禁止出现未定义的营销黑话（如"赋能全链路"）。

### 2.2 三大核心能力（必备 3 条，且每条含 1 个具体事实）
1. **可编排的智能体**：声明式定义工具与流程，支持多步推理与工具调用。
2. **轻量接入**：单文件 SDK，标准 ESM 引入，无强制运行时依赖。
3. **可观测与可控**：内置调用追踪与权限边界，便于调试与审计。

> 每条能力：一个短标题（≤ 8 汉字）+ 两行内说明 + 可选的等宽字体代码/命令片段。

### 2.3 社会证明 / 技术可信度
- 3 个数据指标条（如接入耗时、平均响应、集成项目数），数字必须带单位。
- 1 段简短"为什么选择我们"的对比式说明（3 个差异点，短句）。

### 2.4 行动号召（CTA）
- 主 CTA：`开始接入`（跳快速开始 / 文档）
- 次 CTA：`查看源码`（跳仓库）
- 页尾 CTA：与主 CTA 复用同一文案与样式层级，避免文案分裂。

### 2.5 快速开始（Quick Start）
- 一个代码块：安装命令 + 最小可运行示例（3–5 行）。
- 代码块提供"复制"按钮（见 §5.4）。

## 3. 页面层级（Information Architecture）

单页，自上而下 7 个区块，顺序即阅读顺序，不可任意新增区块（新增需回到 researcher 变更简报）。

```
index.html
└─ 单页 <main>
   1. Header（固定顶栏）
        - Logo / 站名「OwO Agent」
        - 导航：能力 / 快速开始 / 文档 / 源码
        - 右侧主 CTA 按钮
   2. Hero（首屏）
        - 主标题 + 副标题 + 双 CTA
        - 右侧/下方 视觉主体（抽象智能体拓扑示意，非照片）
   3. Capabilities（核心能力）
        - H2 区块标题 + 3 张能力卡片（等宽等高）
   4. Quick Start（快速开始）
        - H2 + 左侧步骤说明（1-2-3），右侧代码块
   5. Proof / Metrics（可信度）
        - 3 个指标 + 1 段差异点说明
   6. Final CTA（页尾引导）
        - 一句收束文案 + 主 CTA
   7. Footer
        - 版权、文档、源码、一个次级链接组（如隐私/联系）
└─ 页面内锚点：#capabilities / #quickstart / #docs / #source
```

层级规则：
- 单一 `<h1>`（Hero 主标题）；每个区块一个 `<h2>`；卡片标题为 `<h3>`。
- 导航项与页面锚点一一对应，不允许出现指向不存在区块的导航。
- 区块间纵向节奏一致（由 styles.css 的 spacing token 统一，见 §6.2）。

## 4. 关键交互（Interaction Spec）

| 编号 | 交互 | 触发 | 期望行为 | 可访问性要求 |
|---|---|---|---|---|
| I1 | 导航跳转 | 点击导航项 | 平滑滚动到对应区块；目标区块顶部不被固定顶栏遮挡（scroll-margin-top） | 键盘 Tab 可达，焦点可见 |
| I2 | 主 CTA | 点击「开始接入」 | 滚动到 #quickstart 或跳文档链接 | 链接语义（`<a>`），有 aria-label 时文案一致 |
| I3 | 代码复制 | 点击代码块「复制」按钮 | 写入剪贴板，按钮文案短暂变为「已复制」，约 1.5s 后复原 | 结果通过 `aria-live="polite"` 播报 |
| I4 | 卡片悬停/聚焦 | 鼠标悬停或键盘聚焦能力卡片 | 轻微抬升 + 边框高亮，无布局位移 | `:focus-visible` 与 `:hover` 同视觉强度 |
| I5 | 移动端菜单 | 视口 < 768px 点击汉堡按钮 | 展开/收起导航；展开时按钮 `aria-expanded=true` | Esc 可关闭；展开层内焦点陷阱 |
| I6 | 减少动效 | 系统 `prefers-reduced-motion: reduce` | 关闭平滑滚动与卡片位移，仅保留透明度变化 | 必测 |

交互非目标：不做表单提交、登录、实时聊天、多语言切换。

## 5. 视觉方向（Visual Direction）

### 5.1 气质关键词
**工程感 / 冷静 / 可信 / 克制的高科技**。参考观感：开发者工具官网（终端、代码、等宽字体、深色底），而非消费品营销页。

### 5.2 色彩
- 深色优先（`#0B0F14` 一类近黑蓝底），正文用高对比浅灰（对比度 ≥ 4.5:1）。
- 单一强调色（建议青蓝 / 电光紫二选一），**只用于**：主 CTA、关键数字、链接 hover、焦点环。
- 语义色：成功（复制完成）、错误（若有），需在深底上通过对比度 AA。
- 必须同时提供浅色方案的可读性回退（可仅通过 CSS 变量定义，不强制实现切换器）。

### 5.3 字体与排版
- 中文：系统无衬线栈（PingFang SC / Microsoft YaHei / Noto Sans SC 回退）。
- 代码与数字：等宽栈（ui-monospace / JetBrains Mono 回退）。
- 排版层级明确：H1 ≥ 40px（桌面）、H2 28–32px、正文 16px、辅助文字 14px；行高正文 ≥ 1.6。
- 中文标题避免字间距过大；不使用全大写英文标题。

### 5.4 图形与组件
- Hero 视觉：抽象"节点 + 连线"拓扑图形，用 CSS/SVG 绘制，禁止外链位图。
- 能力卡片：圆角 12–16px，1px 边框，深色面 + 极轻内发光，等宽等高（宽高比一致）。
- 代码块：等宽字体、行内不换行可横向滚动、「复制」按钮固定右上角，按钮高 ≥ 32px。
- 图标：统一线性图标（stroke 一致），大小 20–24px。

### 5.5 动效
- 仅入场淡入（≤ 300ms，ease-out）与 hover 位移（≤ 2px）；不引入自动轮播、弹窗、视差。
- 所有动效必须响应 `prefers-reduced-motion`。

### 5.6 响应式断点
- ≥1200px：双栏 Hero、三列卡片
- 768–1199px：Hero 单栏居中、两列卡片
- <768px：全单列、汉堡菜单、代码块横向滚动、按钮最小触控尺寸 44×44px

## 6. 技术约束与实现边界（给 designer / builder 的硬约束）

- 交付文件：唯一页面入口 `index.html`，唯一样式表 `styles.css`，二者不得互相内联替代（禁止用大段内联 `<style>` 取代 styles.css）。
- 不得引入构建工具、外链 CDN、位图与第三方字体；仅允许系统字体与内联 SVG。
- 样式必须通过 CSS 变量（token）组织：颜色、间距、圆角、字号、动效时长各成一组。
- 语义化标签：`header/nav/main/section/h2/h3/footer`，交互控件用原生 `<button>` / `<a>`。
- 测试：使用 `node:test`（内置 test runner）对页面做**静态断言**（见 §7）。

## 7. 验收标准（Acceptance Criteria）

### 7.1 内容与结构
- [ ] AC-1 `index.html` 存在且包含唯一 `<h1>`，其文本与 §2.1 主标题一致。
- [ ] AC-2 §3 中 7 个区块全部存在（可用 class/id 断言：header、hero、#capabilities、#quickstart、#proof、#final-cta、footer）。
- [ ] AC-3 能力卡片数量恰为 3，每张卡片含 `<h3>` 标题与说明文本。
- [ ] AC-4 导航 4 个链接的 `href` 均指向页面内真实存在的锚点。
- [ ] AC-5 页面至少 2 处 CTA（主 CTA、页尾 CTA），且文案一致。
- [ ] AC-6 所有图片类视觉为内联 SVG 或纯 CSS，无 `<img>` 外链、无 CDN 引用。

### 7.2 样式与可访问性
- [ ] AC-7 `styles.css` 存在且非空，含 CSS 变量定义块（`--color-` / `--space-` 前缀至少各 1 个）。
- [ ] AC-8 所有交互元素可键盘聚焦，且存在 `:focus-visible` 样式声明。
- [ ] AC-9 存在 `@media (prefers-reduced-motion: reduce)` 规则块。
- [ ] AC-10 存在至少 1 个响应式断点媒体查询，移动端导航为汉堡形态（含 `aria-expanded`）。
- [ ] AC-11 正文文本与背景对比度满足 WCAG AA（设计阶段用配色值自检并记录）。

### 7.3 自动化测试（node:test）
- [ ] AC-12 存在可被 `node --test` 直接执行的测试文件（如 `tests/page.test.js`），无第三方依赖，仅用 `node:fs`、`node:test`、`node:assert`。
- [ ] AC-13 测试覆盖 AC-1、AC-2、AC-3、AC-4、AC-6、AC-7、AC-9（至少 7 个断言组），且全部通过。
- [ ] AC-14 `node --test` 退出码为 0，输出中无失败用例。

> 说明：本简报标注的测试路径 `tests/page.test.js` 属于 builder 实现范围；researcher 仅定义要求，不落地代码。

## 8. 非目标（Out of Scope）

- 不做多页站点 / 路由 / SPA 框架。
- 不做真实后端、API 调用、鉴权与表单提交。
- 不做博客、定价页、多语言（i18n）、暗/亮主题切换器。
- 不做构建打包、TypeScript、CSS 预处理器、CSS-in-JS。
- 不做第三方分析埋点、Cookie 横幅、客服悬浮窗。
- 不做真实动画库（GSAP/Framer 等）与视频背景。
- 不做像素级品牌 VI 延展（logo 仅需文字标识 + 一个简单 SVG 图形）。
- 不追求 Lighthouse 全绿与 SEO 深度优化，仅要求语义化与基础 meta（title/description/viewport）。

## 9. 交给 designer 的下一步

1. 依据 §3 输出 `index.html` 结构与 §6 的约束；样式集中在 `styles.css`。
2. 按 §5 确定色板、字号、间距 token，并在文件头注释记录对比度自检值（对应 AC-11）。
3. 交互按 §4 表逐条实现，重点确认 I1（滚动偏移）、I3（复制 + aria-live）、I5（汉堡菜单 aria-expanded）。
4. 交付前自查 §7.1–7.2 全部勾选项，测试脚本由实现方按 §7.3 补齐。
