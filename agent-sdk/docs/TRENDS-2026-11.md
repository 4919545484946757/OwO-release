## 3. 工具检索（tool search / defer loading）成为刚需

工具数超过约 100 时，"全部塞进上下文"会显著掉准确率；业界做法是**语义检索 + 延迟加载**，
Anthropic Tool Search 报告约 85% token 下降（`defer_loading`）。
来源：[Agentic Landscape 2026](https://github.com/tylerjrbuell/reactive-agents-ts/blob/4d3fe980888c3d0d5239361b1f35077837f978d8/wiki/Research/2026-06-29-agentic-landscape-vs-reactive-agents.md)

**我们的位置**：有 MCP schema 预算压缩与工具名前缀掩码，但**没有**"按需检索工具"。
**实测（2026-11-18，字符数/4 粗估）**：默认工具面 27 个 ≈ **3.8k tok**；加剧本组
（4 个）≈ 4.3k（**Δ0.46k**）；全能力面 57 个 ≈ **6.2k tok**。距"100 工具"阈值还有距离，
所以结论是：**先加预算回归阈值，不急着上检索**；等全能力面接近 80–100 工具再评估
deferred loading。回归测试：`tools::tests::tool_schema_budget_by_capability_group`
（默认 ≤6k / 剧本组 Δ≤0.8k / 全能力 ≤10k tok）。
**下一步**：工具数量继续增长时再引入检索，避免过早复杂化。

## 4. KV-cache 前缀稳定性：掩码而不是移除

生产经验（Manus）：缓存命中 ≈ $0.30 vs 未命中 $3（约 10×）；频繁增删工具会抖动前缀、
让模型引用已消失的工具。原则是 **mask tools, don't remove them**。
来源：同上（Agentic Landscape，Manus 生产指标）

**我们的位置**：MCP 工具已走 `set_tool_prefix_enabled` 掩码而非卸载；可选工具组是
"默认不装配"（这会在开关时改变前缀）。**下一步**：给可选组设计稳定前缀策略
（装配但默认掩码），并加缓存友好性说明。

## 5. 上下文工程的下一阶段是"harness 工程"

LangChain 2026-11 复盘：架构已收敛为"模型循环 + 工具 + 沙箱"，难点转向
上下文重置/状态外置/失败转规则等 harness 层能力。
来源：[LangChain blog](https://www.langchain.com/blog/context-engineering-challenges-late-2026)

**我们的位置**：已有 turn 截止时间、压缩、审计、验收收据、剧本进度外置；
缺的是"失败自动转规则"的闭环。**下一步**：把高频工具失败沉淀为 playbook 的
`check` 断言或 hook（可审计、可回滚）。

## 补充：工作流与持久执行（2026-11 追加调研）

来源：[semarun（语义恢复）](https://pypi.org/project/semarun/0.1.0/)、
[Microsoft Agent Framework：Durable 工作流](https://learn.microsoft.com/ja-jp/agent-framework/hosting/durable-extension)、
[Google ADK 2.0 Changelog（graph workflow runtime）](https://github.com/google/adk-python/blob/54c5fd258ad0889fafea99126d238fdd3a444e64/CHANGELOG-v2.md)、
[TRACK：可恢复的计划](https://zenodo.org/records/20826174)、
[Durable Execution（Reactive Agents）](http://docs.reactiveagents.dev/guides/durable-execution/)。

四条共识：

1. **检查点 ≠ 耐久执行**：真正的问题在"工具已产生副作用、进程在写入结果前崩溃"——需要在
   **派发前**写一条待定记录、**完成后**写终态，恢复时能判定"已发生就注入结果、不要重跑"。
2. **计划本身要可恢复**：TRACK 把 plan 当作恢复对象（任务契约、强制校验、失败分类、定向
   补任务、恢复点治理），而不是只重放对话。
3. **图运行时成为标准形态**：路由、fan-out/fan-in、循环、重试、共享状态、HITL、嵌套工作流。
4. **语义恢复优于全文重放**：按已完成的语义单元续跑，避免重跑已通过的步骤浪费 token。

**与我们的对照**（有源码依据）：

| 能力 | 现状 |
|---|---|
| 计划可恢复 | ✅ `playbook` 状态文件逐步骤 passed/failed/skipped + evidence，`/advance --playbook` 重启后从状态继续 |
| 图校验 | ✅ `validate`（依赖存在/无环/未知依赖）与拓扑序 |
| 快照/对比 | ✅ archive/history/diff（含退化） |
| HITL | ✅ `human` 步骤 + 面板记录 |
| 重试 | ⚠️ 只有 attempts 计数与手动重试；无每步策略（次数/退避） |
| 失败分类 | ⚠️ 只有 exit code 与文本证据，没有分类（环境/代码/依赖） |
| **工具副作用 exactly-once** | ❌ 命令成功但状态未落盘时，恢复会重跑（潜在重复副作用） |
| 并行/嵌套 | ❌ 顺序执行 |

**建议的下一步（按性价比）**：

1. **check 派发前置日志**：`playbook_check` 执行前写"待定"记录、执行后写终态；恢复时若发现
   待定且无终态 → 明确标记"结果未知，需人工确认"，而不是静默重跑。这是最小代价的
   durable 语义。
2. 每步重试策略（`max_attempts`/退避）进 schema，默认沿用当前行为（不改变已有剧本语义）。
3. 失败分类字段（`failure_kind`）用于 `diff` 与面板聚合。
