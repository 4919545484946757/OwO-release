# 多智能体 Agent 框架：发展方向与功能建设目标



参考原文链接：[来看看这段聊天](https://chatgpt.com/share/6afdbfdf-cd08-83ea-a18c-3e810b6f523f)



建议将这套框架定位为一个以共享上下文为基础、以工作流为组织形式、以统一记忆为长期知识载体、以多智能体协同为执行方式的通用 Agent Runtime（智能体运行时框架）。

它不应仅仅是对 LLM API 的封装，也不应该只是让多个 Agent 相互发送消息，而是需要提供完整的智能体生命周期管理、任务调度、上下文治理、知识积累、工具调用、状态管理和执行环境。

最终实现从单 Agent 执行到多 Agent 自主协同，从预定义工作流到动态任务规划，从一次性任务执行到具备长期记忆的持续工作。

## 三、核心功能模块建设目标

### 1. 共享上下文系统（Shared Context System）

建议作为整个框架最核心的差异化功能。

传统的多 Agent 协作如果主要依赖历史消息转发，容易出现上下文重复、信息孤岛、任务目标偏移和 Token 浪费。

应当建立独立于任意 Agent 和 LLM 的共享上下文中心。

Agent 按权限读取、提交和订阅上下文变化，而非复制完整对话历史。

| 功能             | 建设目标                              |
| ---------------- | ------------------------------------- |
| 全局共享上下文   | 保存项目目标、规则、约束、技术规范    |
| 工作空间上下文   | 保存特定项目的文件、环境与知识        |
| 工作流上下文     | 保存当前流程的执行状态与中间结果      |
| 任务上下文       | 保存子任务目标、依赖关系与执行进度    |
| Agent 私有上下文 | 保存角色设定、局部状态和临时信息      |
| 动态上下文组装   | 根据当前任务选择相关信息注入模型      |
| 上下文压缩       | 摘要、去重、信息提取与历史裁剪        |
| 上下文版本控制   | 支持快照、变更记录、差异比较与回滚    |
| 上下文订阅       | Agent 可订阅特定信息的变化            |
| 上下文冲突处理   | 处理并行 Agent 修改同一信息产生的冲突 |
| 上下文预算       | 根据模型窗口和任务重要程度分配 Token  |
| 上下文溯源       | 记录信息来源、更新时间、作者和可信度  |

上下文需要支持分层继承：

01

Organization Context

组织规范、全局规则与权限

02

Workspace Context

项目资料、环境与技术架构

03

Workflow Context

流程目标、共享变量与依赖

04

Task Context

任务要求、输入与输出约束

05

Agent Session Context

角色指令与当前局部执行状态

每个 Agent 不需要拥有完全相同的上下文，而是共享同一个事实与状态来源，并根据自身任务获得不同的上下文视图。

这比简单地建立一个所有 Agent 都可以读写的全局字典更加重要。

### 2. 多智能体协同系统（Multi-Agent Collaboration）

支持自主 Agent 的定义、注册、组队、协作、分工、监督与退出。

| 功能                | 建设目标                             |
| ------------------- | ------------------------------------ |
| Agent Registry      | 智能体注册、发现、版本管理           |
| Agent Profile       | 定义角色、目标、能力、工具和行为约束 |
| Capability Registry | 根据能力匹配合适的智能体             |
| Dynamic Team        | 根据任务动态组建 Agent 团队          |
| Task Delegation     | 智能体之间自主委派子任务             |
| Parallel Execution  | 无依赖任务并行执行                   |
| Agent Communication | 单播、广播、订阅、请求响应           |
| Agent Handoff       | 在智能体之间移交任务及相关状态       |
| Supervisor          | 监督执行过程、纠正任务偏移           |
| Agent Review        | 不同 Agent 之间交叉审查和验证        |
| Conflict Resolution | 解决结论冲突、资源冲突和任务冲突     |
| Agent Replacement   | 智能体执行失败时替换执行者           |
| Collaboration Limit | 限制委派深度、通信次数和执行预算     |

应当支持多种协作拓扑，而不是绑定在固定的 Supervisor 架构上。

中心化监督模式

Supervisor 统一分配、监督与汇总任务。

去中心化协作模式

对等 Agent 彼此通信、协商和委派。

流水线协作模式

任务沿多个专业 Agent 顺序处理。

分层递归协作模式

复杂任务递归拆解，各子团队独立执行。

黑板协作模式

Agent 通过共享任务池、事实和事件领取任务、贡献结果并触发后续行动。

其中，黑板模式（Blackboard Pattern）尤其适合作为共享上下文架构的基础协作方式，并结合 Supervisor 实现全局任务控制。

### 3. 自定义工作流引擎（Agentic Workflow Engine）

工作流不能只支持固定的 DAG（有向无环图），因为 Agent 执行过程中还需要循环、动态分支、任务重试、自我反思与计划调整。

应支持三种工作方式：

| 模式       | 说明                                         |
| ---------- | -------------------------------------------- |
| 静态工作流 | 用户预先定义节点、执行顺序和条件             |
| 动态工作流 | Planner 根据任务目标实时生成执行流程         |
| 混合工作流 | 用户定义整体骨架，Agent 自主决定局部执行路径 |

混合工作流应当作为重点建设方向，兼顾执行的确定性与智能体自主性。

动态拆解、并行执行、汇聚验证、失败重新规划。

具体需要支持的工作流节点：

| 节点类型         | 用途                     |
| ---------------- | ------------------------ |
| Agent Node       | 调用指定智能体           |
| LLM Node         | 直接调用语言模型         |
| Tool Node        | 调用外部工具             |
| Code Node        | 执行自定义代码           |
| Condition Node   | 根据条件选择执行分支     |
| Router Node      | 根据规则或语义动态路由   |
| Parallel Node    | 并行执行多个任务         |
| Join Node        | 同步与汇聚并行执行结果   |
| Loop Node        | 反复执行直到满足终止条件 |
| Planner Node     | 动态生成后续任务         |
| Evaluator Node   | 评估任务结果             |
| Memory Node      | 读写统一记忆             |
| Human Node       | 等待人工审批或输入       |
| Event Node       | 等待或发送特定事件       |
| Subworkflow Node | 嵌套并复用已有工作流     |
| Transform Node   | 进行数据结构转换         |

除此之外，工作流需要支持变量传递、结构化输入输出、节点级超时、条件重试、断点恢复、版本管理、子流程复用、定时触发、Webhook 触发与事件驱动触发。

最终提供 Python/TypeScript 等 SDK、YAML/JSON 声明式配置以及可视化拖拽工作流编辑器。

### 4. 统一记忆系统（Unified Memory System）

记忆系统不应等同于向量数据库，也不应该简单地保存所有对话记录，而应建立一套完整的记忆生命周期管理机制。

Agent 观察 · 用户反馈 · 工具结果 · 执行经验

信息提取 → 分类 → 去重 → 可信度评估

工作记忆

当前任务与临时状态

情景记忆

历史事件与执行经历

语义记忆

事实、知识与概念

程序性记忆

工作策略、技能与操作流程

混合检索 · 重排序 · 记忆关联 · 冲突消解

上下文组装 → Agent 决策与执行

| 功能                 | 建设目标                             |
| -------------------- | ------------------------------------ |
| Working Memory       | 当前执行过程中的临时工作记忆         |
| Episodic Memory      | 保存历史任务、事件与执行轨迹         |
| Semantic Memory      | 保存事实、知识、规则与概念           |
| Procedural Memory    | 保存成功策略、操作流程与技能         |
| Shared Memory        | 多 Agent 共享的组织或项目记忆        |
| Private Memory       | 特定 Agent 独有的长期记忆            |
| Memory Extraction    | 从交互和执行过程中提取有效信息       |
| Memory Consolidation | 将重复、分散的信息合并为知识         |
| Hybrid Retrieval     | 关键词、向量、图关系与元数据混合检索 |
| Temporal Memory      | 根据时间、有效期和版本管理记忆       |
| Memory Forgetting    | 清理过期、冗余或错误记忆             |
| Memory Governance    | 记忆权限、来源、审核、修改和删除     |
| Experience Replay    | 检索与当前任务相关的历史执行经验     |

必须明确区分三个容易混淆的概念：

| 系统    | 主要解决的问题                   |
| ------- | -------------------------------- |
| Context | Agent 在本次推理时需要知道什么？ |
| Memory  | 系统过去积累了什么可复用的信息？ |
| State   | 当前任务实际上执行到了什么阶段？ |

记忆可以作为上下文组装的数据来源，但不能替代任务状态，更不能覆盖经过明确确认的项目约束。

### 5. 自主任务规划与调度系统（Planning & Scheduling）

让框架具备从用户目标出发，自主拆解、分配、执行和调整任务的能力。

核心功能包括：

- Goal Management： 目标管理、目标优先级、成功条件定义。

- Task Decomposition： 将复杂目标拆解为可执行原子任务。

- Dependency Analysis： 自动识别任务之间的前置依赖。

- Dynamic Planning： 根据当前状态生成后续执行计划。

- Replanning： 根据失败、环境变化或新信息重新规划。

- Capability Matching： 根据 Agent 能力和工具权限分配任务。

- Resource Scheduling： 管理并发数、模型请求额度和执行资源。

- Critical Path： 识别影响整个任务完成时间的关键依赖路径。

- Speculative Execution： 在预算允许时并行尝试多个候选方案。

- Task Cancellation： 取消不再必要的任务并管理相关副作用。

- Termination Detection： 判断任务是否完成，防止无限循环执行。

例如，在多 Agent 软件开发场景中：

框架自动识别任务依赖，使可以并行的开发工作同时进行。

规划器负责决定做什么，调度器负责决定由谁做、何时做，执行器负责具体怎么做。这三个模块应当保持独立。

### 6. Agent 生命周期与运行时管理（Agent Runtime）

建立类似进程管理器的 Agent 运行机制，使智能体成为具有显式身份、状态、资源和生命周期的逻辑执行单元，而不是一个临时 Prompt。

生命周期示意：支持暂停、恢复、等待、失败重试与终止等状态转换。

| 功能                     | 建设目标                            |
| ------------------------ | ----------------------------------- |
| Instance Management      | 创建、销毁和管理 Agent 实例         |
| Session Management       | 支持独立会话和长期会话              |
| State Machine            | 显式维护生命周期状态                |
| Checkpoint               | 保存可恢复的执行状态                |
| Crash Recovery           | 服务重启后恢复未完成任务            |
| Timeout Control          | 防止任务无限等待                    |
| Retry Policy             | 支持退避、次数限制与错误分类        |
| Resource Quota           | 管理 CPU、内存、Token 和费用预算    |
| Distributed Runtime      | 支持多进程、多节点部署              |
| Concurrency Control      | 控制 Agent 并行数量以及共享资源访问 |
| Cancellation Propagation | 父任务取消时向子任务传播            |

运行时需要能够支持长时间任务、异步任务、人类审批任务以及跨会话继续执行的任务。

### 7. 统一工具与技能系统（Tool & Skill System）

工具是原子执行能力，技能是经过组织和验证的复合工作能力。

例如，读取文件属于工具，而完成一次完整的代码审查属于技能，可以由多个工具、规则、Prompt 和子工作流组合而成。

| 功能              | 建设目标                        |
| ----------------- | ------------------------------- |
| Tool Registry     | 统一注册内置与外部工具          |
| MCP Integration   | 接入 MCP 服务提供的工具与资源   |
| Tool Schema       | 标准化工具输入、输出及错误描述  |
| Tool Discovery    | Agent 根据任务动态发现工具      |
| Tool Router       | 从多个可用工具中选择合适工具    |
| Tool Permission   | 按 Agent 和工作空间管理工具权限 |
| Tool Sandbox      | 隔离代码、命令和浏览器执行环境  |
| Tool Result Cache | 缓存适合复用的工具结果          |
| Tool Middleware   | 调用前后拦截、日志、验证和审计  |
| Skill Registry    | 注册和发现复合技能              |
| Skill Composition | 将多个工具组合为高层技能        |
| Skill Versioning  | 技能版本管理与兼容性检查        |
| Skill Evaluation  | 对技能的有效性与可靠性进行测试  |

长期可以发展独立的技能生态，使开发者无需修改框架核心代码即可扩展 Agent 能力。

### 8. 统一模型网关（Model Gateway）

框架不应将任何一个 Agent 与某个特定 LLM 强绑定，而是提供统一模型接口，由网关负责模型选择和请求调度。

| 功能                | 建设目标                        |
| ------------------- | ------------------------------- |
| Model Adapter       | 适配不同模型供应商和本地模型    |
| Model Registry      | 管理模型能力、配置和访问凭证    |
| Intelligent Routing | 根据任务难度和能力需求选择模型  |
| Model Fallback      | 模型不可用时切换备用模型        |
| Load Balancing      | 在多个模型实例之间负载均衡      |
| Rate Limiting       | 管理 RPM、TPM 和并发请求限制    |
| Structured Output   | 支持结构化输出与 Schema 验证    |
| Multimodal Support  | 支持文本、图像、音频和视频输入  |
| Token Accounting    | 统计各 Agent 的 Token 消耗      |
| Budget Control      | 限制单任务、单 Agent 和全局成本 |
| Response Cache      | 对适用请求进行安全的结果缓存    |
| Embedding Gateway   | 统一管理向量模型接口            |
| Rerank Gateway      | 统一管理检索重排序模型          |

实现不同复杂程度的任务使用不同能力等级的模型，避免所有 Agent 无差别调用高成本模型。

### 9. 共享工作空间与产物管理（Artifact & Workspace）

这是多 Agent 协同中非常容易被忽略的模块。

Agent 之间传递的不应只有自然语言消息，还应包括代码、文件、结构化数据、测试报告、研究结果、设计方案与决策记录等正式产物。

Workspace

共享工作空间示例

context/

项目目标、约束与上下文快照

tasks/

任务定义、依赖与状态

artifacts/

Agent 生成的正式交付产物

knowledge/

项目知识与参考资源

decisions/

架构决策与变更记录

skills/

可复用技能定义

workflows/

工作流配置

checkpoints/

执行恢复点

evaluations/

测试与评估记录

功能目标包括产物注册、结构化元数据、版本控制、来源追踪、产物依赖关系、并发修改检测、文件锁、独立分支、变更合并、结果复用与审核发布。

对于软件开发类型的 Agent，还应支持 Git 工作树隔离、独立代码分支、补丁提交、自动化测试和合并冲突处理。

共享上下文、共享记忆、共享工作空间共同构成多个智能体的协同基础。 但共享并不意味着允许所有 Agent 无限制地修改同一份数据。

### 10. Agent 通信与事件驱动系统（Event Bus）

建立框架内部统一的事件通信机制，使各模块和 Agent 之间实现松耦合。

| 事件类型            | 触发含义            |
| ------------------- | ------------------- |
| `task.created`      | 新任务创建          |
| `task.assigned`     | 任务已分配          |
| `task.completed`    | 任务成功完成        |
| `task.failed`       | 任务执行失败        |
| `context.updated`   | 共享上下文发生变化  |
| `memory.written`    | 新记忆写入          |
| `artifact.created`  | 新产物生成          |
| `artifact.conflict` | 产物发生版本冲突    |
| `agent.spawned`     | 创建新的 Agent 实例 |
| `agent.finished`    | Agent 完成当前运行  |
| `workflow.paused`   | 工作流暂停          |
| `approval.required` | 等待人工审批        |
| `budget.exceeded`   | 超出资源预算        |

事件系统还应支持发布订阅、消息队列、持久化事件、事件重放、消息优先级、关联 ID、消息去重和幂等处理。

例如，测试 Agent 订阅 `artifact.created` 事件，在相关代码产物生成之后自动接收测试任务，而不需要所有 Agent 持续进行轮询或者互相询问进度。

### 11. 自我反思、验证与纠错系统（Reflection & Verification）

为 Agent 建立完整的执行反馈闭环。

具体能力包括自我审查、独立 Agent 审查、多模型交叉验证、规则验证、结构化输出验证、事实核查、工具结果检测、自动化测试、失败原因分析和重新执行。

特别需要建立多层验证机制：

| 验证层级    | 主要方法                       |
| ----------- | ------------------------------ |
| L1 格式验证 | JSON Schema、类型和字段约束    |
| L2 规则验证 | 业务规则、明确约束和权限检查   |
| L3 环境验证 | 实际执行、编译、测试与工具反馈 |
| L4 语义验证 | LLM 判断结果是否符合任务目标   |
| L5 独立验证 | 不同 Agent 或独立模型进行复核  |
| L6 人工验证 | 高风险、高价值任务人工审批     |

确定性的测试结果应当优先于模型的主观评价。不能让一个 Agent 仅仅通过另一段自然语言评价，就认定实际任务已经成功。

### 12. 人机协同系统（Human-in-the-loop）

用户应当能够随时加入正在执行的任务，而不是只能等待最终结果。

| 功能              | 建设目标                   |
| ----------------- | -------------------------- |
| Live Intervention | 实时介入 Agent 执行        |
| Approval Gate     | 敏感操作执行前审批         |
| Task Redirect     | 中途修改任务目标或方向     |
| Context Injection | 执行过程中补充资料和约束   |
| Plan Review       | 审核 Agent 生成的任务计划  |
| Result Correction | 人工修正结果并触发后续处理 |
| Manual Assignment | 将特定任务指定给特定 Agent |
| Execution Control | 暂停、恢复、终止和重新执行 |
| Feedback Capture  | 将用户反馈转化为可复用经验 |
| Autonomy Level    | 配置 Agent 的自主执行程度  |

权限模式可以划分为以下四级：

| 自主等级      | 行为方式                                       |
| ------------- | ---------------------------------------------- |
| L0 建议模式   | 只提供方案，不执行操作                         |
| L1 审批执行   | 关键操作需要逐次确认                           |
| L2 约束内自主 | 在指定范围和预算内自主执行                     |
| L3 高度自主   | 自主规划、执行、验证与调整，仍受权限和预算约束 |

### 14. 安全与权限体系（Agent Security）

Agent 具备工具调用能力之后，安全模块必须成为底层运行机制，而不是后期附加功能。

| 功能                     | 建设目标                               |
| ------------------------ | -------------------------------------- |
| Agent Identity           | 为每个 Agent 建立独立身份              |
| RBAC / ABAC              | 角色与属性访问控制                     |
| Least Privilege          | 最小权限分配                           |
| Workspace Isolation      | 不同工作空间数据隔离                   |
| Execution Sandbox        | 文件、网络、进程与命令隔离             |
| Credential Vault         | 集中管理 API Key 和访问凭证            |
| Prompt Injection Defense | 防止外部资料中的恶意指令获得执行权限   |
| Data Classification      | 对数据进行敏感程度分级                 |
| Policy Engine            | 统一执行安全策略                       |
| Audit Log                | 记录所有关键操作                       |
| Emergency Stop           | 紧急终止智能体与任务                   |
| Side-effect Control      | 控制删除、支付、发送、部署等外部副作用 |

必须将来自外部文件、网页和其他 Agent 的内容视为数据，不能因为它出现在共享上下文中，就自动具备修改系统规则或扩大工具权限的能力。

### 15. 自动评估与持续进化系统（Evaluation & Evolution）

系统需要能够衡量自身的工作质量，而不仅仅是完成任务。

| 评估维度      | 主要指标                                 |
| ------------- | ---------------------------------------- |
| 任务完成质量  | 成功率、结果正确率、目标满足程度         |
| 多 Agent 协同 | 并行效率、重复工作率、通信开销           |
| 上下文质量    | 信息命中率、上下文利用率、过期信息使用率 |
| 记忆效果      | 检索准确率、历史经验复用率               |
| 执行效率      | 总耗时、关键路径耗时、任务吞吐量         |
| 资源消耗      | Token、费用、工具调用数量                |
| 系统可靠性    | 失败恢复率、异常率、重复执行率           |
| 自主能力      | 人工干预次数、重新规划成功率             |
| 安全性        | 越权操作率、策略拦截效果                 |

持续进化的主要方向应当包括 Prompt 优化、技能沉淀、工作流优化、Agent 角色调整、模型路由策略优化以及历史成功经验复用。

不建议早期实现无限制的 Agent 自我修改。更合理的方式是由 Agent 提出优化方案，在独立测试环境进行验证，通过评估之后再发布新版本。

## 四、需要重点解决的底层工程问题

上述功能决定了框架的能力上限，而下面这些问题决定了框架是否真正可用。

| 工程问题                    | 建议解决方案                           |
| --------------------------- | -------------------------------------- |
| 多 Agent 同时修改共享上下文 | 版本控制、乐观锁、事务提交与冲突检测   |
| 并行任务重复执行            | 唯一任务 ID、任务认领机制、幂等处理    |
| Agent 使用过期信息          | 上下文版本标记、变更订阅、执行前校验   |
| Agent 之间信息污染          | 信息来源标记、可信度分级、写入权限控制 |
| 长任务中途服务崩溃          | 状态持久化、Checkpoint、断点恢复       |
| 无限循环和递归委派          | 最大步数、最大深度、时间与预算限制     |
| 多 Agent 消息数量膨胀       | 事件过滤、通信预算、结构化消息         |
| 长上下文导致注意力分散      | 按需检索、分层上下文、动态组装         |
| 多 Agent 结论相互矛盾       | 依据证据仲裁、独立验证、人工介入       |
| 外部工具产生不可逆操作      | 审批机制、幂等键、执行前检查、补偿事务 |
| 工作流修改后无法复现        | 固定工作流、模型配置、技能与上下文版本 |
| Agent 生成错误记忆          | 候选记忆审核、来源追踪、冲突检测       |

尤其要注意：多 Agent 协作本质上也包含分布式系统问题。 不能将协调、一致性、状态恢复、安全权限等问题全部交给 LLM 通过自然语言处理。

## 五、框架核心抽象设计

建议在代码层面建立统一的领域对象，而不是围绕某种具体 Agent 实现硬编码。

| 核心对象           | 职责                 |
| ------------------ | -------------------- |
| `Agent`            | 智能体定义与能力描述 |
| `AgentInstance`    | 智能体运行实例       |
| `Team`             | 智能体协作团队       |
| `Goal`             | 任务目标与成功标准   |
| `Task`             | 可独立调度的任务单元 |
| `Plan`             | 动态任务计划         |
| `Workflow`         | 工作流定义           |
| `WorkflowRun`      | 工作流执行实例       |
| `Context`          | 上下文数据对象       |
| `ContextStore`     | 共享上下文存储       |
| `ContextAssembler` | 动态上下文组装器     |
| `Memory`           | 记忆数据对象         |
| `MemoryStore`      | 统一记忆存储         |
| `StateStore`       | 任务及执行状态存储   |
| `Artifact`         | 正式任务产物         |
| `Workspace`        | 共享工作空间         |
| `Message`          | Agent 通信消息       |
| `Event`            | 系统事件             |
| `Tool`             | 原子工具能力         |
| `Skill`            | 可复用复合能力       |
| `Policy`           | 权限和执行策略       |
| `Evaluator`        | 评估与验证器         |
| `Checkpoint`       | 执行状态恢复点       |
| `Trace`            | 全链路执行记录       |

核心接口之间应当允许自由替换。例如 MemoryStore 可以使用不同数据库实现，Planner 可以基于规则、LLM 或传统搜索算法实现，Scheduler 可以使用本地调度器或分布式调度器实现。

这才是框架与具体 Agent 应用之间的本质区别。

## 六、框架架构设计原则

| 设计原则                 | 具体要求                                       |
| ------------------------ | ---------------------------------------------- |
| Context First            | 将上下文作为一等公民，而非 Prompt 附属数据     |
| State First              | 重要执行状态由程序维护，而不是依赖 LLM 记忆    |
| Event Driven             | 使用事件实现模块之间的松耦合                   |
| Model Agnostic           | 不绑定任何单一模型或供应商                     |
| Agent Agnostic           | 不限制具体 Agent 推理策略                      |
| Composability            | Agent、工具、技能、工作流均可组合              |
| Extensibility            | 通过插件和接口扩展，不修改框架核心             |
| Durable Execution        | 长任务具备持久化、恢复与重试能力               |
| Structured Communication | 使用明确的数据协议进行任务和产物交换           |
| Observable by Design     | 从框架设计初期建立全链路观测                   |
| Security by Design       | 从底层限制权限与执行行为                       |
| Bounded Autonomy         | 在明确目标、规则和预算内进行自主执行           |
| Progressive Complexity   | 支持从简单单 Agent 逐步扩展为复杂多 Agent 系统 |

## 九、核心竞争力建设建议

如果要让这套框架具备独立的技术价值，而不是另一个常规的 Agent 编排框架，我建议集中研发以下五个方向。

| 核心竞争力                  | 重要程度 |
| --------------------------- | -------- |
| 动态共享上下文与一致性管理  | P0       |
| 多 Agent 自主协同与任务调度 | P0       |
| 动态工作流生成与执行        | P1       |
| 统一记忆与经验持续积累      | P1       |
| 可验证、可恢复的自主执行    | P1       |

以上方案按照通用 Agent 框架设计，并将多 Agent 并行软件开发作为首个复杂应用验证场景；优先级和版本划分属于建议，尚未绑定具体编程语言、基础设施或现有框架，也未经过实际性能验证。

最终，整个项目可以确立一个统一的研发宗旨：

让多个智能体在共享知识、共享上下文、共享状态的环境中，通过可编排、可调度、可验证、可恢复的机制，自主协同完成复杂任务，并将执行过程中积累的知识和经验转化为可持续复用的系统能力。
