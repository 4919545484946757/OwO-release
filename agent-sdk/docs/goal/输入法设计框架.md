参考链接：[来看看这段聊天](https://chatgpt.com/share/6afdc6e5-d24c-83ea-8e32-98040dcc81d8)

这样产品的定位就比较明确了：以轻量化输入法为主体，以动态语境感知为核心，以大模型为增强引擎，而不是把整个 Agent 平台塞进输入法。

AI 不应该只是一个等待用户调用的附加工具，也不应该接管所有输入过程。它应该在后台理解用户所处的语境，动态调整输入法自身的策略，在真正需要生成和推理时才进一步介入。

暂时按照 Windows 桌面端优先进行设计。

# 一、重新确定产品核心定位

我建议将整个产品收敛为五个核心系统。

| 核心系统       | 主要职责                                   |
| -------------- | ------------------------------------------ |
| 基础输入系统   | 保证传统输入法的完整性、速度和稳定性       |
| 动态语境系统   | 感知应用环境、话题、输入内容与用户习惯     |
| 自适应策略系统 | 实时调整词库、候选排序、预测与 AI 介入程度 |
| AI 增强系统    | 文本生成、理解、修改、翻译、多模态输入     |
| 轻量扩展系统   | 模型接入、自定义指令、工具与有限记忆       |

不再将多 Agent 协同、复杂工作流编排、完整知识库管理作为输入法自身的核心职责。

# 二、核心创新：动态语境驱动输入

这是整个产品最值得投入研发的部分。

目前的设计不应该只是简单地判断用户正在使用微信还是 Word，然后切换对应的词库。而应该建立多层次、持续变化的语境。

## 2.1 五层语境模型

| 语境层级 | 感知内容                     | 变化频率   |
| -------- | ---------------------------- | ---------- |
| 应用语境 | 当前软件、窗口类型           | 切换应用时 |
| 任务语境 | 写代码、写论文、聊天、搜索   | 切换任务时 |
| 话题语境 | 强化学习、材料学、软件开发等 | 随内容变化 |
| 即时语境 | 光标前后文本、当前输入句子   | 实时变化   |
| 个人语境 | 用词习惯、术语偏好、表达风格 | 长期更新   |

例如，即使用户一直在使用浏览器，其实际语境也可能不断变化。

当前应用：浏览器

正在使用 GitHub

技术讨论 · 英文术语 · 代码优先

正在使用在线文档

正式表达 · 长文预测 · 中文优先

正在使用即时聊天

口语表达 · 短句预测 · 网络用语

正在使用搜索引擎

关键词输入 · 实体名称 · 减少长句补全

因此，应用只是语境判断的依据之一，不能直接决定所有输入策略。

## 2.2 动态候选词调整

传统输入法主要利用拼音匹配、语言模型、词频、用户词库等信息。

我们可以在此基础上引入一个动态语境评分机制：

\[
S(w)=\sum_{i=1}^{n}\alpha_i f_i(w)
\]

其中评分特征包括：

- \(f_1\)：拼音匹配程度。

- \(f_2\)：基础词频。

- \(f_3\)：当前文本语义相关性。

- \(f_4\)：专业领域相关性。

- \(f_5\)：个人使用习惯。

- \(f_6\)：应用及任务语境。

- \(f_7\)：近期使用频率。

核心在于权重 \(\alpha_i\) 不再固定，而是由语境策略引擎动态调整。实际实现时需要对各项评分进行尺度校准。

下面是一个简单的交互示意。

### 动态输入策略演示

概念原型

当前语境：日常口语

# moshi

提高日常词频和个人习惯权重。候选及权重仅用于说明策略变化，实际参数需通过实验确定；扩展短语与精确拼音候选应当区分。

大模型的作用不一定是直接生成候选词，也可以是理解当前语境，然后为传统输入引擎提供调控信息。

例如，大模型或轻量分类模型可以生成以下策略：

```
{
  "domain": "software_engineering",
  "topic": "multi_agent",
  "language": "zh-CN",
  "style": "technical",
  "dictionary": [
    "computer_science",
    "artificial_intelligence"
  ],
  "prediction_mode": "phrase",
  "completion_level": 0.3,
  "english_term_priority": 0.8,
  "cloud_generation": "on_demand"
}
```

随后传统输入引擎按照策略调整自己的行为。

大模型负责理解语境，策略引擎负责控制输入行为，传统引擎负责高速执行。

这样既能够深度结合 AI，又不需要把每次按键都发送给大模型。

## 2.3 策略的动态更新机制

语境策略不应该每次按键都重新计算，而应该采用事件驱动、缓存与增量更新的方式。

| 触发事件             | 后台行为                 |
| -------------------- | ------------------------ |
| 切换应用             | 加载对应的应用策略       |
| 切换窗口             | 判断任务是否发生变化     |
| 开始输入             | 获取可用的局部文本上下文 |
| 连续输入多个句子     | 更新话题语境             |
| 用户选择非首位候选词 | 记录偏好，调整后续排序   |
| 用户反复拒绝 AI 补全 | 降低主动补全频率         |
| 用户频繁使用专业术语 | 提高对应词库权重         |
| 语境发生明显变化     | 重新计算输入策略         |
| 网络或模型不可用     | 自动退回本地输入策略     |

还需要增加策略稳定机制，避免因为偶然出现一个词，就导致整个输入模式发生剧烈变化。

例如，用户在技术文档中偶尔输入一句日常表达，系统不应该马上切换为聊天模式。

# 三、AI 介入程度：自适应分级机制

AI 介入不应当只有开启和关闭两个选项，而应当是连续可调的。

L0

纯传统输入

只进行拼音转换、词库匹配和基础预测。

L1

后台语境增强

自动感知语境、调整词库和候选排序，不主动生成长文本。

L2

轻量主动预测

提供短语、句尾补全、智能纠错和术语建议。

L3

生成式输入

提供完整句子、段落、意图扩展和文本重构。

L4

主动 AI 任务

用户明确发起检索、分析、工具调用、复杂内容生成。

建议默认采用 L1，系统可以依据当前语境自动在 L1～L2 之间调整，L3 和 L4 则通过用户主动操作启动。

例如：

| 使用场景         | 默认介入策略                 |
| ---------------- | ---------------------------- |
| 即时聊天         | L1～L2，短句和回复预测       |
| 正式文档         | L2，长句预测，可主动进入 L3  |
| 编程环境         | L1，专业术语与中英混输       |
| 搜索框           | L1，关键词和实体优化         |
| 终端             | L0～L1，避免生成内容误触执行 |
| 密码及敏感输入   | 禁止 AI 感知、记录及上传     |
| 主动发起 AI 指令 | 临时进入 L3 或 L4            |

用户可以覆盖自动策略，例如对某个软件永久关闭生成式补全。

# 四、功能收敛：哪些做，哪些不做

为了避免臃肿，我建议按照下面的范围重新筛选此前的功能。

## 4.1 必须实现的核心功能

智能输入

拼音转换、动态词库、语义候选排序、智能纠错、中英混输、专业术语识别。

语境感知

应用识别、任务判断、局部文本理解、话题识别、策略动态调整。

生成式补全

短语补全、句子续写、关键词扩展、意图驱动输入。

AI 文本编辑

润色、翻译、扩写、精简、语气调整、自定义自然语言修改。

AI 语音输入

流式语音识别、口头语整理、语义重构、语音指令。

轻量个人记忆

个人词库、常用术语、表达偏好、应用策略、用户主动保存的信息。

快捷指令系统

自定义 Prompt、参数引用、快捷键、AI 功能统一调用。

模型管理

本地与云端模型接入、BYOK、模型路由、服务降级。

## 4.2 可以作为可选扩展的功能

| 功能          | 实现方式                 |
| ------------- | ------------------------ |
| AI 剪贴板     | 轻量历史记录与内容理解   |
| 截图识别      | 用户主动调用多模态模型   |
| 联网搜索      | 作为一个独立工具         |
| 文件引用      | 按需读取用户选择的文件   |
| 数学公式转换  | 专用输入技能             |
| 自定义 Skills | 配置文件或插件形式       |
| MCP 工具调用  | 可选 MCP Client          |
| 简单工作流    | 支持线性指令组合         |
| 外部 Agent    | 通过统一接口调用         |
| 跨设备同步    | 可选服务，不作为核心依赖 |

## 4.3 不建议内置的功能

| 功能                    | 原因                       |
| ----------------------- | -------------------------- |
| 完整多 Agent 调度框架   | 与输入法核心职责无关       |
| 可视化 DAG 工作流编辑器 | 开发复杂度高，使用频率低   |
| 完整 RAG 知识库平台     | 可以通过外部工具接入       |
| 自主电脑控制 Agent      | 权限、稳定性与安全问题较多 |
| 完整 AI 聊天平台        | 已有大量成熟产品           |
| 复杂文档编辑器          | 输入法应服务于现有编辑器   |
| 后台持续屏幕监控        | 隐私及资源消耗问题         |
| 大规模长期任务管理      | 交由外部 Agent 系统处理    |

不是放弃这些能力，而是通过接口将其外部化。

你正在规划的多 Agent 框架可以作为一个独立系统，未来输入法只需要提供调用接口，共享经过授权的任务上下文即可，不需要重复实现一套 Agent Runtime。

# 六、轻量化的模型调度方案

轻量化不仅是减少功能，也意味着减少模型调用、内存占用、推理延迟和网络依赖。

建议采用四级计算体系，而不是所有任务都调用统一的大模型。

01

传统算法与规则

最高频

拼音匹配、词典检索、基础排序、快捷指令、应用识别

02

本地轻量模型

高频

语境分类、候选重排序、短语预测、语义匹配

03

快速生成模型

按需

润色、翻译、句子补全、语音重构

04

高能力大模型

低频

复杂推理、长内容生成、多模态理解、工具调用

条形长度表示预期使用频率的相对关系，不是实际性能测试结果。

其中后台语境分析完全可以优先使用规则、轻量分类模型和语义向量模型。只有当语境难以确定或者任务确实需要复杂理解时，才调用大模型。

同时设立初步的工程性能目标：

| 指标             | 建议目标                     |
| ---------------- | ---------------------------- |
| 基础按键处理     | 5ms 以内                     |
| 本地候选词返回   | 20ms 以内                    |
| 缓存语境策略加载 | 10ms 以内                    |
| 后台语境更新     | 异步，不阻塞输入             |
| AI 补全          | 尽可能低延迟，支持流式输出   |
| 云端服务异常     | 不影响基础输入               |
| 本地模型         | 支持关闭、按需加载和空闲卸载 |
| 常驻资源占用     | 尽量接近轻量传统输入法       |

这些是建议设计指标，最终需要结合硬件与原型测试确定。

# 七、还可以重点创新的几个功能

相比继续添加外部工具，我更倾向于深入开发输入法自身的智能化能力。

## 7.1 自适应个性化学习

不仅记录用户选择过哪些词，还要学习用户如何使用输入法。

例如用户经常拒绝长句补全，但经常接受专业术语补全，那么系统应该自动减少长句生成，提高专业短语预测。

可以利用以下反馈信号：

- 候选词选择位置。

- AI 补全接受率。

- 生成内容修改比例。

- 纠错接受或拒绝情况。

- 不同应用下的功能使用频率。

- 用户主动修改的语境策略。

初期用统计学习和在线权重更新即可，后续可以考虑 Contextual Bandit（上下文多臂老虎机）进行自适应策略优化，不需要直接训练大型模型。

# 八、建议的模块化开发路线

| 阶段     | 开发目标               | 核心模块                                |
| -------- | ---------------------- | --------------------------------------- |
| 第一阶段 | 可独立使用的基础输入法 | 输入引擎、词库、候选栏、系统适配        |
| 第二阶段 | 自适应智能输入法       | 语境管理、动态策略、候选重排序          |
| 第三阶段 | AI 原生输入法          | 生成式补全、意图输入、AI 编辑、模型管理 |
| 第四阶段 | 多模态输入法           | AI 语音、截图识别、智能剪贴板           |
| 第五阶段 | 轻量开放生态           | Skills、MCP、外部 Agent、策略插件       |

所有扩展模块都应该支持独立启停，核心输入进程不应该直接承担 AI 推理或者外部工具执行任务。

# 九、下一步需要重点讨论的设计

我觉得目前有一个比 Agent 功能更重要的问题：是否要重新设计用户表达意图的输入机制。

原则上可以支持四种输入方式：

| 模式     | 用户输入示例                   | 预期行为               |
| -------- | ------------------------------ | ---------------------- |
| 精确输入 | 逐字输入拼音                   | 保持用户原始表达       |
| 预测输入 | 本系统采用统一的               | 预测后续内容           |
| 意图输入 | 多agent 并行 共享记忆 避免冲突 | 将关键词组织成完整表达 |
| 指令输入 | 把刚才那段改成正式技术说明     | 对内容执行指定操作     |

前三者解决文字输入效率，最后一种解决内容控制效率。

我的建议是保留传统输入模式作为默认，通过快捷键临时进入意图输入模式，让用户可以直接输入零散关键词、混合语言甚至不连贯的语句，由 AI 组织表达。同时支持语音意图输入。

最终，我们需要做的不是一款功能最多的 AI 输入法，而是一款能够自主适应使用环境、动态改变输入行为、按需调用智能能力的轻量化输入法。

这个定位下，动态语境、策略引擎和意图驱动输入才是真正的研发核心，其他 AI 功能都围绕这三个核心展开。
