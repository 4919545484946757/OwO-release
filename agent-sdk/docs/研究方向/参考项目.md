# 为什么多 Agent 并行开发，反而不如一个强 Agent？

你的观察确实有研究依据，而且这可能正是下一代 Coding Agent 最值得突破的问题之一。

截至 2026 年 10 月，已经有实证研究发现：多个 Agent 同时工作，不仅不能保证软件开发质量提升，还可能因为推理上下文被拆散、任务依赖被错误判断、共享代码状态不一致，导致整体表现退化。

但也有最新研究证明：通过改进共享工作区的状态感知与协调机制，两个 Agent 可以显著优于单 Agent。

这说明问题并不一定是多智能体协作本身不可行，而是当前的协作机制还没有足够有效地组织多个智能体进行复杂软件开发。

## 二、为什么单 Agent 往往写得更好？六个根本原因

结合上述论文和 Codex、Claude Code 的实际架构，我认为软件开发中的质量退化主要来自六类问题。

### 原因 1：全局推理被拆散，这是最核心的问题

一个强单 Agent 开发复杂功能时，会不断积累对整个项目的认识：

- 项目原有设计为什么这样安排？

- 某个模块与其他模块有哪些隐含依赖？

- 之前为什么放弃某种实现？

- 改动某个接口会影响哪些调用方？

- 哪个测试失败反映了真正的根本原因？

这些信息并不只是代码文件，而是模型在持续推理过程中形成的项目理解和决策历史。

多 Agent 拆分任务后，假设 A 负责后端，B 负责前端：

A 可能认为登录成功应返回：

```
{
  "user": {"id": 123},
  "access_token": "..."
}
```

B 则按照自己理解编写：

```
const token = response.data.token;
const userId = response.data.userId;
```

两人各自编写的代码可能都符合自己的局部假设，但组合之后无法工作。

即使他们共享同一个项目目录，也不意味着共享同一套推理上下文。

物理共享代码 ≠ 语义共享认知。

这正是单 Agent 的天然优势：同一个推理主体持续负责规划、实施、反馈和修复，较少发生决策意图在交接过程中丢失的问题。

### 原因 2：任务分解往往破坏软件本身的依赖结构

软件开发并不是把一个大任务简单拆成几个小任务就能并行。

设开发任务由一个依赖图表示：

\[
G=(V,E)
\]

其中 \(V\) 为任务集合，\(E\) 为任务间依赖。

如果把 10 个任务分配给 5 个 Agent，但其中 8 个任务存在强依赖，实际可并行的工作可能非常少。

低耦合任务

三个相对独立的开发链可以并行

高耦合任务

任务之间需要频繁同步与返工

这导致一个悖论：

> 越复杂的软件开发任务，越需要多个 Agent 分担工作；但复杂任务往往也具有更强的耦合性，越难安全地并行。

因此，当前按“前端 Agent、后端 Agent、测试 Agent”固定分工的方法太粗糙。

合理的任务边界应该依据实际代码依赖、数据契约、修改范围和可独立验证性决定，而不是角色名称。

### 原因 3：多个 Agent 对工作区的认知存在时间差

这是你提出的“所有 Agent 共用一个工作区”必须解决的问题。

考虑两个 Agent：

Agent A

负责修改用户服务

Agent B

负责修改登录流程

| T1  | 都读取 `auth.ts` 的 V1 版本 |
| --- | --------------------- |
| T2  | A 写入 V2，更改函数参数        |
| T3  | B 仍依据 V1 推理并写入        |
| T4  | 出现覆盖、旧接口调用或隐藏回归       |

更麻烦的是，即使 Agent B 发现文件发生了修改，它此前已经形成的计划也未必会自动更新。

因此需要管理两个不同的状态：

文件状态：当前代码实际是什么？

认知状态：Agent 是基于哪个代码版本、哪些设计假设做出的决定？

PASC 主要改善前者的活动感知，而完整的协同开发系统还需要解决后者。

### 原因 4：多 Agent 增加了错误传播路径

假设一个强单 Agent 作出了错误的 API 设计，它还有机会在随后运行测试和调试时修正。

但多 Agent 环境中，主 Agent 作出错误设计后，可能立即把这个错误分发给三个子 Agent。

于是：

- 前端按照错误接口编码。

- 后端按照错误数据库设计编码。

- 测试 Agent 也可能依据同一份错误规格编写测试。

最终大家的实现可能完全一致，但一致地实现了错误需求。

这是共享错误假设（Common-mode Failure），并非通过增加 Agent 数量就能避免。反而可能因为多个 Agent 都支持同一份错误规格，制造错误的信心。

### 原因 5：主 Agent 从开发者退化成了消息转发者

在一些多 Agent 工作流中，主 Agent 将任务拆分出去后，只负责接收各队员的“完成报告”。

这意味着最重要的整体设计、实际代码验证和跨模块修复没有明确负责人。

理想的主 Agent 需要拥有最终代码的解释权和修改权，而不是仅仅把子 Agent 的回答总结成一段文字。

关键问题不是“有没有 Team Lead”，而是 Team Lead 是否真正承担端到端工程责任。

### 原因 6：局部测试通过不代表产品完成

例如：

- 前端组件测试全部通过。

- 后端 API 测试全部通过。

- 数据库模块测试全部通过。

- 但前端与后端协议不一致。

- 登录功能在真实浏览器中失败。

甚至测试 Agent 自己生成的测试也可能遗漏用户真实要求。

最终出现三个 Agent 都报告成功，但整个产品质量仍不如单 Agent 的情况。

Claude Code 官方文档也明确表示，对顺序依赖强、同文件修改多、跨模块依赖密集的任务，单 Agent 或轻量子 Agent 可能更有效；并强调多 Agent 会增加协调开销。

## 三、我建议的新架构：质量优先的自适应协作系统

我不建议继续采用传统的：

`主 Agent → 分配任务 → 并行编码 → 汇总结果`

而建议设计一个暂称 Quality-Preserving Adaptive Swarm（QPAS） 的架构。这是下面提出的设计方案名称，不是已发表的系统。

它的核心思想是：

保留强单 Agent 的连续推理和全局控制能力，同时让其他 Agent 在确实能增加收益的地方并行工作。

### 3.1 第一项改进：主 Agent 始终保持全局工程认知

系统需要有一个始终存在的 Principal Engineer Agent。

它不是单纯的调度器，而是：

- 维护整体架构和用户验收目标。

- 处理无法安全并行的关键路径。

- 决定是否接受子 Agent 的代码变更。

- 对整个项目运行和最终交付负责。

其他 Agent 是可动态创建、暂停、合并的执行者。

这样就不会因引入并行而完全丢失单 Agent 的优势。

### 3.2 第二项改进：不再强制所有任务并行

每个待执行任务先由系统判断使用哪种协作模式。

动态调度决策示意

选择一种任务，查看建议的协作模式。以下耦合分数仅用于演示，不是实测模型输出。

修改统一认证中间件

增加三个独立数据导入器

排查难以复现的性能问题

完成跨前后端的新功能

示意耦合程度

68/100

分阶段混合执行

先统一设计契约，独立实现阶段并行，随后进行集成和端到端验收。

我建议把调度决策建立在五类信息上：文件写入重叠度、模块调用依赖、API 契约稳定性、任务是否能独立验证、协作预计成本。

调度器不应只根据任务数量决定 Agent 数量，而应估计：

\[
U_{\mathrm{parallel}}
=
T_{\mathrm{saved}}
-
T_{\mathrm{coord}}
-
P_{\mathrm{failure}}\cdot T_{\mathrm{repair}}
\]

其中：

- \(T_{\mathrm{saved}}\)：并行预计节省的时间。

- \(T_{\mathrm{coord}}\)：通信、同步和验证开销。

- \(P_{\mathrm{failure}}\)：协作失败的估计概率。

- \(T_{\mathrm{repair}}\)：失败后的预计修复时间。

这只是可以用于构建调度器的初始效用函数；概率和时间需要通过真实执行日志学习或估计，而不能让 LLM 随便生成数字。

如果并行预计收益为负，系统应该自动退化成单 Agent。

允许不并行，才可能真正做好自适应并行。

### 3.3 第三项改进：共享的不只是文件，而是决策、契约和执行证据

我建议引入三个不同的共享层：

| 层      | 内容                   | 作用              |
| ------ | -------------------- | --------------- |
| 共享工作区  | 文件、代码、Git 状态         | 所有 Agent 面对同一项目 |
| 共享决策记录 | 设计约束、API 契约、已确认的技术选择 | 保持语义一致性         |
| 共享执行事实 | 文件变更、测试结果、错误日志、任务状态  | 消除过期认知          |

共享决策记录尤其重要。

例如，后端 Agent 决定修改登录字段时，不是给前端发送一句“我把字段改了”，而是提交一个正式的契约变更事件，说明旧字段、新字段、影响范围及版本。

调度器根据代码依赖关系，找到受影响的 Agent，要求它们更新计划。

这样可以避免两个 Agent 虽然在同一个目录里开发，却对项目架构持有完全不同的认知。

### 3.4 第四项改进：把共享目录变成受控的协作环境

你希望多个 Agent 在同一个工作区协作，这没有问题，但它需要一个统一的写入管理层。

共享项目代码

唯一权威工作区

Workspace State Manager

快照版本 · 变更检测 · 写入授权 · 依赖分析 · 冲突处理

Agent A

读 / 提交补丁

Agent B

读 / 提交补丁

Agent C

读 / 提交补丁

Agent 先读取代码版本，再提出修改补丁。提交时：

1. 检查原始文件版本是否仍然有效。

2. 检查有没有其他 Agent 正在修改受影响区域。

3. 没有冲突则原子应用补丁。

4. 发现版本冲突则返回差异，让 Agent 重新推理。

5. 通过测试后才将变更标记为已验收。

这不是要求所有 Agent 串行执行。大部分读取、推理、检索、代码生成和独立模块写入仍能并发，只对存在冲突风险的共享资源进行约束。

文件层控制不能自动解决语义冲突，因此还需要类型检查、接口契约测试和端到端验证。Shell、Git 命令和代码生成器产生的副作用也必须处于受控执行环境中，否则它们可以绕过写入管理层。

## 四、完整开发流程应该怎么设计？

我建议使用阶段性并行，而不是全过程并行。

1. 理解与设计阶段：主 Agent 负责
   
   先分析代码仓库、用户需求、现有架构和测试体系，建立统一规格与验收标准。只有关键接口确定后，才允许涉及这些接口的实现任务开始。

2. 并行调查阶段：多个 Agent 独立思考
   
   对复杂问题并行调查不同方案、检索代码、发现潜在风险。调查结果由主 Agent 综合，并记录设计决策。这个阶段主要并行化推理，通常不修改共享代码。

3. 实施阶段：根据实际依赖动态执行
   
   低耦合任务由多个 Agent 同时编码；高耦合区域使用单写入者。每个任务都有明确的输入版本、允许修改范围和验收测试。

4. 持续同步阶段：事件驱动的选择性通知
   
   文件、接口和依赖发生重要变化时，只通知受影响的 Agent。发生契约变更时，可暂停依赖任务，先由主 Agent 确认后再恢复。

5. 全局验证阶段：独立审查 + 实际执行
   
   自动执行编译、类型检查、单元测试、接口兼容测试和端到端测试。审查 Agent 检查实现是否满足原始需求，而不仅仅是代码有没有报错。

6. 增量修复阶段：定位责任，再重新调度
   
   不把所有错误重新交给整个团队。根据失败测试、变更历史和依赖关系，定位最可能的根本原因，只重新启动必要的 Agent。

这个架构中，最重要的不是给每一步都分配一个专门角色，而是建立一套可恢复、可验证、有明确责任归属的协作协议。

## 五、如何证明你的方案真正优于 Codex 和 Claude Code？

我建议不要直接以“能不能完成一个演示项目”作为验证标准，而要做严格的消融实验。

| 实验组 | 配置                            | 验证的问题      |
| --- | ----------------------------- | ---------- |
| A   | 强单 Agent                      | 质量基线       |
| B   | Codex / Claude Code 原生多 Agent | 现有协作效果     |
| C   | 多 Agent + 共享执行状态              | 状态感知是否有效   |
| D   | C + 动态任务调度                    | 自适应并行是否有效  |
| E   | D + 共享决策记录                    | 语义同步是否有效   |
| F   | E + 受控写入 + 全局验收               | 完整系统是否优于基线 |

每组尽量使用同等级模型、相同测试环境和相同初始仓库，并分别在固定 Token 预算、固定时间预算下比较。每个任务要重复运行，以避免一次随机结果造成误判。

需要测量的不仅是开发时间，还包括：

- 最终任务成功率：独立隐藏测试是否通过。

- 功能完整率：用户需求中的功能是否真正实现。

- 回归率：是否破坏原有功能。

- 人工纠正次数：用户需要反复补充多少次指令。

- 端到端完成时间：包括修复失败与重新执行的时间。

- 实际成本：包括所有子 Agent、测试和失败重试。

还可以定义一个很有研究价值的指标：

\[
\text{Quality-Adjusted Speedup}
=
\frac{Q_{\mathrm{multi}}/T_{\mathrm{multi}}}
{Q_{\mathrm{single}}/T_{\mathrm{single}}}
\]

其中 \(Q\) 是统一标准下的任务质量得分，\(T\) 是端到端时间。

但不能只看这个比值。例如质量从 90 分降到 70 分，时间减半，指标仍然可能提高。因此，应该先设定质量不得显著退化的约束，再优化时间和成本。

在科研实验中，可以使用预先设定的非劣效界限，并结合置信区间检验，而不是仅凭平均分说质量差不多。

建议使用两类基准：一类是 SWE-bench Pro、Commit0 等代码修复或开发任务；另一类是完整产品开发任务，检验设计一致性、功能集成与端到端体验。仅依赖 SWE-bench 不能完整说明一个应用开发团队的能力。

## 七、我的最终判断

我认为你可以将研究重点从普通的 Multi-Agent Coding 转向：

面向共享软件工作区的质量保持型自适应多智能体协作。

它与现有方案的区别应当是：

| 当前常见方案            | 值得突破的方案                   |
| ----------------- | ------------------------- |
| 复杂任务尽量拆分给多个 Agent | 根据预期收益和风险自动决定并行程度         |
| Agent 交换自然语言消息    | 共享可验证的代码状态、设计决策和执行证据      |
| Agent 各自完成局部任务    | 全局功能完整性由系统持续验证            |
| 修改冲突后再解决          | 写入前检测版本与依赖冲突              |
| 主 Agent 主要负责协调    | 主 Agent 保留全局工程责任与关键路径实施能力 |
| 优先提高并行数量          | 在质量约束下优化交付速度和成本           |

作为实际开发路线，我建议第一版只有一个强主 Agent 和最多两个并行工作 Agent，先研究共享状态、任务分配和质量验证。随后才逐步扩大 Agent 数量。因为目前的研究还不足以证明 Agent 越多越好，反而已有证据表明更大的团队可能产生明显干扰。

如果是作为科研项目，我会把创新重点集中在动态并行决策、语义级共享状态同步、基于执行证据的失败定位与增量修复这三个方向。它们之间存在明确的联系，也能通过消融实验分别验证。

真正值得实现的，不是一个同时干活的 AI 程序员团队，而是一个知道什么时候应该协作、什么时候不应该协作，并且能持续保证最终产品质量的开发系统。

你说的其实是 Single-Conversation Multi-Agent Collaborative Coding（单对话驱动的多智能体协同编程）。

不是让用户开多个 Codex 或 Claude Code 窗口，也不是每个 Agent 在不同 Git worktree 里独立开发、最后合并。

你希望的是：

- 一个对话入口：用户只需要输入一次任务，并能继续与主 Agent 交流。

- 多个真正并行的 Agent：主 Agent 自动创建多个工作 Agent，分别承担编码、测试、调研等任务。

- 同一个工作区：所有 Agent 可以读取同一份项目代码，彼此的修改能够立即被感知。

- 实时协作：Agent 可以交换消息、重新分配工作、处理文件冲突，而不是各干各的。

- 统一交付：主 Agent 负责协调、验证并向用户反馈整个项目的进展。

## 二、最应该精读的论文：STORM

Multi-agent Collaboration with State Management · 2026 年 5 月 · arXiv 预印本

论文

完整研究代码

这篇论文几乎就是在研究你想解决的核心问题：

多个 Coding Agent 在同一工作区并发修改代码，怎样避免状态冲突？

它不是通过给每个 Agent 创建独立 worktree 来解决，而是在 Agent 和共享文件系统之间增加一个状态管理层。

基本流程是：

1. Agent A 读取 `auth.py` 的版本 V1。

2. Agent B 也读取 V1，并率先写入 V2。

3. Agent A 随后尝试基于旧版本 V1 写入。

4. STORM 检查版本依赖，识别到过期写入，拒绝修改并返回最新状态，让 Agent A 重新调整实现。

这是一种把冲突提前到写入时发现的方法。论文还研究了跨文件上下文依赖与语义冲突。

![](https://www.google.com/s2/favicons?domain=https://www.researchgate.net&sz=32)

ResearchGate

+1

论文报告，STORM 相比基于 Git worktree 的多智能体基线，在 Commit0-Lite 上提升 18.7 个评分点，在 PaperBench 上提升 1.4 个评分点。它的公开仓库还提供 OpenHands SDK、Docker 和多 Agent 实验相关实现。

我建议以 OpenCode 或 Codex 的 Coding Agent 执行能力 + 自研协作调度层 + STORM 式状态管理 为起点。

| 组件              | 技术选择                                  |

| 主 Agent、子 Agent | Codex / OpenCode SDK，或自己实现 Agent Loop |
| 并发任务调度          | TypeScript + Promise / 异步任务队列         |
| Agent 通信        | 内部事件总线 + 结构化邮箱                        |
| 工作区             | 唯一项目目录 + 统一文件工具接口                     |
| 写入控制            | 文件版本号、Hash、乐观并发控制                     |
| 代码理解            | Tree-sitter + LSP + ripgrep           |
| 数据持久化           | SQLite（MVP）                           |
| 模型接入            | OpenAI-compatible API / LiteLLM       |
| 自动验证            | Git 快照 + 编译 + 单元测试 + 集成测试             |

我特别建议你不要在第一版引入过于复杂的多 Agent 框架，因为你的主要研究对象就是协作调度本身。调度器尽量自主实现，底层文件操作、模型调用和沙箱尽量复用成熟组件。

还有一个非常关键的技术决定：

所有 Agent 可以同时读取共享代码，但修改共享代码时，应尽量通过统一的受控写入服务。

例如 Agent A 和 B 都要修改 `auth.py`，可以同时进行推理、准备修改方案，但最终写入由状态管理器根据文件版本和变更范围决定是否允许提交。否则，任何直接运行的 Shell 命令都可能绕过文件版本检查。

这不妨碍多个 Agent 真正并行工作，只是对共享状态的修改进行协调。

## 四、你的创新空间究竟在哪里？

现在的 Codex 和 Claude Code 已经能解决一个对话创建多个并发 Agent的问题。

但目前仍值得研究的是：

让多个 Agent 像人类结对编程或软件团队一样，在同一份不断变化的代码上保持一致认知，动态协商、分工和修改，而不仅仅是一次性派工。

最值得研究的具体问题，是如何把以下机制整合起来：

动态分工 + 实时消息 + 共享工作区版本控制 + 语义级冲突检测 + 受影响任务的增量修复。

这可以构成有科研价值的完整系统。

我的建议是：先精读 Codex 的多 Agent 源码与 STORM，再研究 Oh My OpenAgent 的团队通信实现。 这三项组合起来，比研究 Superset、Vibe Kanban 等多工作区管理产品更贴近你的真实目标。

# 多智能体并行软件开发 Agent：2026 年项目与技术路线调研

你的方向已经有比较成熟的技术基础，但仍然存在值得突破的问题。

截至 2026 年 10 月，已经出现了 Superset、Vibe Kanban、Agent Orchestrator 等开源或源码可用的产品，它们能够同时运行多个 Claude Code、Codex、OpenCode 等 Coding Agent，分别处理不同开发任务。

![](https://www.google.com/s2/favicons?domain=https://github.com&sz=32)

GitHub

+2

因此，仅仅实现“一个用户同时管理多个 Coding Agent”，已经不足以形成明显的技术创新。

真正值得研究的是：

> 用户只描述一次复杂开发需求，系统便自动理解现有代码库、拆解任务、建立依赖关系，动态组织多个智能体并行编码、交换必要信息、发现冲突、集成测试，并最终交付一个可工作的完整项目。

这里存在三个不同的技术层次：

| 层次                 | 能力                    | 技术难点        |
| ------------------ | --------------------- | ----------- |
| L1：多会话并行           | 多个 Agent 在不同工作区执行任务   | 较低，已有成熟实现   |
| L2：自动协同开发          | 自动规划、分工、依赖调度、合并与测试    | 中高，是实用产品的核心 |
| L3：自适应 Agent Swarm | 动态组队、跨任务协商、自动重规划、失败恢复 | 高，仍有研究空间    |

我建议你以 L2 作为产品起点、L3 作为研究目标，不要从头训练新的 Coding Agent，而是先构建能够调用不同底层模型和开发工具的协同编排系统。

## 三、推荐技术架构：怎么真正实现并行开发？

我更推荐采用 中心调度 + 动态任务图 + 隔离执行 + 自动集成 的混合架构。

### 3.3 并行工作的三个关键技术问题

#### 问题一：任务自动分解不等于任务可并行

例如，用户提出：

> 开发一个包含用户登录、权限管理、管理后台与自动化测试的 Web 系统。

规划 Agent 可以生成如下依赖图：

A：定义数据库 Schema 和 API 契约

B：后端 API

C：前端 UI

D：测试用例

E：系统集成与端到端验证

这里 B、C、D 可以在 A 的接口契约确定后同时开始，并不需要等后端实现完成才开始编写前端。

但如果测试 Agent 要执行真实接口测试，它仍然需要等待 B 完成。因此任务本身还需要区分“测试设计”“测试实现”“测试运行”等不同阶段。

一个更精确的任务表示可以是：

```
type DevTask = {
  id: string;
  title: string;
  dependencies: string[];
  ownedPaths: string[];
  readOnlyPaths: string[];
  inputContracts: string[];
  outputContracts: string[];
  acceptanceTests: string[];
  baseCommit: string;
  estimatedCost?: number;
  maxAttempts: number;
  status:
    | "blocked"
    | "ready"
    | "running"
    | "review"
    | "passed"
    | "failed";
};
```

真正困难的并非生成任务清单，而是：

1. 正确识别语义依赖和隐藏的共享状态。

2. 判断哪些任务可以安全并行。

3. 当前置任务发生变化时，自动更新后续 Agent 的上下文和任务状态。

这也是动态任务图研究的核心。

#### 问题二：如何防止多个 Agent 改坏同一仓库？

最实用的基础方案是 Git worktree。官方 Git 支持在同一仓库下维护多个工作目录，分别检出不同分支。

![](https://www.google.com/s2/favicons?domain=https://git-scm.com&sz=32)

git-worktree Documentation

```
git worktree add -b agent/backend ../task-backend HEAD
git worktree add -b agent/frontend ../task-frontend HEAD
git worktree add -b agent/tests ../task-tests HEAD
```

这样三个 Agent 可以在不同文件目录中同时修改代码，互不覆盖工作目录。

但worktree 只能解决文件系统级的隔离，不能解决代码语义冲突。例如后端把接口字段从 `userId` 改成 `uid`，前端和测试都可能继续使用旧字段，即使 Git 合并时没有一行冲突，程序依然不能工作。

因此还需要三个机制：

- 接口契约优先：开发前确定 OpenAPI、类型定义等共享契约。

- 代码归属控制：Agent 可以读取整个仓库，但默认只能修改被分配的路径。

- 集成验证：将补丁合并到临时集成分支，运行测试，失败时生成带错误上下文的修复任务。

特别注意，共享的数据库、测试端口、缓存和环境变量也需要隔离。worktree 不会自动隔离这些外部资源。

#### 问题三：Agent 如何真正交换信息？

不建议让所有 Agent 持续参与一个公共群聊。这样会产生大量重复上下文、无意义通信，而且还可能造成相互误导。

更合理的是 Agent 局部上下文 + 结构化消息 + 共享事实存储。

例如一个后端 Agent 发现 API 契约需要调整，向前端发送：

```
{
  "event": "contract.change_proposed",
  "source": "backend-agent",
  "targets": ["frontend-agent", "test-agent"],
  "taskId": "auth-002",
  "artifact": "openapi.yaml",
  "change": {
    "field": "userId",
    "proposedField": "uid"
  },
  "status": "awaiting_approval"
}
```

调度器应该先确认契约变更是否合法，再通知受影响的 Agent 更新工作，而不是直接信任单个 Agent 发出的变更事件。

我建议采用类似 Event Sourcing 的机制，持久化关键事件，并让每个 Agent 只订阅自己依赖的事件。

这使系统不再依赖一个无限增长的主聊天窗口来承载全部开发状态。

## 四、产品真正可以创新的地方

如果我来设计这款产品，会把创新点集中在三个方面，而不是增加 Agent 数量。

创新点 A：依赖感知的动态并行调度

Agent 执行过程中发现新任务、接口冲突或前置依赖变化，系统动态修改 DAG，决定创建、暂停、合并或取消 Agent。核心是让并行度随任务结构变化，而不是始终启动固定数量的 Agent。

创新点 B：Agent 间的最小必要协作

基于代码符号引用、文件依赖、接口契约构建通信图。只有相关 Agent 交换信息，避免全部上下文广播。可以研究如何降低通信 Token 开销并保持系统级一致性。

创新点 C：并行执行与自动质量闭环

不把 Agent 声称的“任务完成”作为成功标准，而是要求自动合并、运行测试并检查回归。如果发现失败，只重新调度受影响的任务，而不是让所有 Agent 从头工作。

这些机制可以形成一个比较明确的科研问题：

能否利用动态依赖图和结构化通信，在软件工程任务中提高多智能体并行效率，同时降低协作冲突和额外 Token 消耗？

需要特别警惕“Agent 越多越强”的直觉。2026 年一项软件工程 Agent 能耗研究发现，其测试配置下多 Agent 方案相较于非 Agent 基线，平均能耗达到 6.36 倍、运行耗时达到 6.07 倍，而准确率提升并不普遍。这个结果不能直接推广到所有并行开发任务，但足以说明为什么要把效率和成本一起纳入评价。

## 五、建议的 MVP 开发路线

01

先实现多 Agent 可靠并发

支持打开 Git 仓库、启动 2～4 个不同工作区的 Coding Agent、查看实时事件、暂停、恢复和查看 Diff。优先使用 Codex / OpenCode SDK，而不是自己编写完整的编码执行循环。

02

加入自动规划和任务 DAG

单一用户需求自动拆解成可验证的任务，生成依赖与文件归属约束。调度器并行启动就绪任务，自动等待前置任务完成。

03

完成自动集成与失败修复

增加临时集成分支、自动测试、冲突定位、修复重试和人工审批。到了这一步，才初步形成完整的软件交付型 Agent。

04

再加入自适应 Swarm

利用历史任务成功率、文件依赖和资源利用率，自动决定 Agent 数量、模型分配、通信对象与重规划策略，并与固定调度策略做实验对比。

如果使用你此前的 RTX 5090 32GB 和本地 Qwen 量化模型环境，可以先让所有 Agent 共享一个 vLLM 推理服务，通过并发请求实现协作。不要假设能同时运行四个 256K 上下文的完整 Agent 且性能不下降；模型 KV Cache、Prefill 和 Decode 会竞争显存与算力。建议先控制在 2～3 个活跃 Coding Agent，再按吞吐、延迟与任务完成时间决定是否扩容。

### 如何证明它确实优于单 Agent？

至少需要设计如下实验：

| 测试方案                  | 作用         |
| --------------------- | ---------- |
| 单一强模型 Coding Agent    | 基线         |
| 多 Agent，人工拆分任务        | 测试纯并行带来的收益 |
| 多 Agent，自动静态 DAG      | 测试自动规划能力   |
| 多 Agent，动态 DAG + 通信   | 测试协作创新     |
| 多 Agent，动态 DAG + 自动集成 | 测试端到端交付效果  |

在同一代码任务集、相同模型条件和可比较预算下，观察任务解决率、实际完成时间、Token 成本、合并冲突率、测试通过率及人工干预次数。可以从 SWE-bench Verified、SWE-PolyBench 和自行构造的多模块功能开发任务开始。

重点不只是提高 benchmark 分数，而是测量真正的端到端交付效率。
