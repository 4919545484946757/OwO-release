# Agent 发展方向与 OwO Agent SDK 设计建议

更新时间：2026-10-13

## 前言：从“会回答”走向“可交付的执行系统”

Agent 的能力演进可以从工程角度看成几个逐步叠加的层次：模型理解与生成、工具调用、由状态和条件控制的工作流、跨轮次任务执行与恢复，以及在适合时进行多 Agent 协作。多 Agent 不是能力的简单相加；规划、沟通、共享状态、冲突处理和结果整合都会消耗时间与模型预算，也会引入新的失败路径。

因此，下一阶段的重点不应只是增加 Agent 数量或角色，而是让系统能根据任务依赖、并行收益、代码冲突风险和验证成本，选择合适的执行方式；同时让任务状态、权限、变更和验证结果可追踪、可恢复。对工程 Agent 来说，用户最终需要的是满足要求、经过验证、可交付的变更，而不是一组看起来完成的子任务。

## 研究给出的设计约束

1. **并行只适用于有真实独立性的工作。** Agent 扩展研究发现，任务可并行性、单 Agent 基线、工具开销和协调拓扑都会改变协作收益；顺序依赖任务可能退化。不能把增加 worker 数当成默认优化。
2. **协调需要显式工件和可检查的状态。** MAST 将多 Agent 失败分为系统设计、Agent 间失配、验证与终止问题。单靠自然语言角色提示不足以形成可靠协作。
3. **共享工作区与隔离工作区各有适用面。** CAID 展示中心规划、异步执行、独立 worktree 与测试集成；PASC 研究同一 Git 工作区中的动作可见性；STORM 研究基于状态版本检查的写冲突处理。论文设置不同，结果不能直接横向排名。系统应把隔离和共享都作为可选执行策略，并明确状态同步与写入边界。
4. **验收必须落到端到端交付。** 子任务完成、局部测试通过或模型自评都不能单独证明全局目标完成。最终验证应针对将要交付的确切代码版本，并覆盖用户目标、失败项、取消/恢复以及审计信息。
5. **工作流既需要模型决策，也需要确定性控制。** 对权限判定、租约、状态迁移、预算、重试、幂等、产物哈希和最终门禁，优先使用可测试的确定性规则；让模型负责理解、提议和有限范围内的修复。

## 建议的目标架构

```text
用户目标
  → 目标规格与验收条件
  → 依赖图 / 风险与并行收益估计
  → 自适应调度（单 Agent、顺序子任务、并行 worker、隔离 worktree）
  → 受权限与租约约束的执行
  → ChangeSet / Artifact 与版本化状态
  → 集成、测试、审查与失败定位
  → 面向原任务的修复或人工决策
  → 交付门禁与可复核结果
```

每个执行单元建议有稳定身份：`task_id + attempt_id + epoch + input_revision`。完成结果应关联实际变更快照、运行命令与退出码、验证器版本、产物引用和审查状态。旧 epoch 的迟到结果不得覆盖新一轮状态；重试和恢复应保持幂等。

### 规划与调度

- 计划由任务依赖图表达，任务定义输入、完成条件、文件/资源范围和验证方式。
- 调度器只并行执行依赖已满足、写范围兼容、预期收益大于协调成本的任务。
- 对高耦合、单文件、强顺序任务默认单 Agent 或串行执行；对独立调查、不同模块且共享契约明确的任务允许并行。
- 运行期间依据任务完成、阻塞和依赖变化重新计算 ready 集，而非固定角色流水线或强制整批等待。
- 始终有一个明确的集成责任方对整体目标和最终变更负责。

### 状态、工作区与写入控制

- 分离任务板、持久事件、共享事实、文件版本、Artifact/ChangeSet 和 Worker 的短期上下文；“能看到同一个文件”不代表“共享同一套认知”。
- 共享工作区需要工作区 revision、读集/写集校验、租约或原子写入、重叠变更检测、动作事件广播和恢复流程。
- 隔离 worktree 需要依赖感知的任务拆分、基础提交身份、合并冲突处理、版本匹配的验证和失败返修流程。
- 依据风险选择执行模型：小且低风险的同树改动可用受控写入；高冲突、不同依赖或需要独立验证的任务优先隔离。
- 角色提示、实际工具注册表和策略权限应由同一份最终 Worker Profile 派生，避免提示和工具权限漂移。

### 验证、恢复与交付

- 将用户验收条件转成可观察的检查项，并关联责任人、运行器和证据来源。
- 集成后在最终变更快照上运行必要的格式、编译、契约、集成或产品检查；保留逐项状态、退出码和未覆盖范围。
- 审查反馈必须有明确消费者和修复路径；失败时回到原任务所有者或有限权限的集成者，而不是把全部工作无差别重做。
- 处理取消、超时、服务重启、租约过期和网络错误时，验证状态机、持久化与重复提交的语义。
- 成功门禁不能被局部 worker 的“完成”状态绕过；未验证、失败和配置缺失应在结果中明示。

## 面向 OwO 的研究与开发优先级

1. **自适应协作策略**：用任务依赖、修改范围、历史冲突率、单 Agent 基线能力与估算协调成本决定是否并行、并行数和工作区拓扑。
2. **共享状态的新鲜度**：让 Agent 知道其计划基于哪个代码/Artifact revision；检测读集过期，要求重规划或定向返修。
3. **真正的交付闭环**：由单一权威门禁汇总目标覆盖、命令结果、测试证据、审查意见和变更身份。
4. **异步任务图与恢复**：明确 attempt/epoch、超时、取消、租约、持久队列和重试幂等规则。
5. **协调效率与上下文质量**：测量上下文组装、等待、模型、工具、返修和集成各段成本；共享事实要带来源、版本和验证状态。
6. **安全的扩展能力**：权限默认拒绝、最小写入范围、秘密脱敏、可审计审批和外部执行隔离贯穿 worker、MCP、命令和自动化流程。

## 建议的验证设计

至少比较强单 Agent、当前 Team、异步隔离 worktree、受控共享工作区四种配置；在相同模型、任务、预算、环境、工具权限和成功条件下多次运行。除端到端成功率外，同时记录：

- 目标满足率、独立测试通过率、回归率和审查阻断项；
- 端到端时间、关键路径、worker 等待、调度/集成/返修时间；
- 输入输出 token、工具调用数和实际成本；
- 冲突率、重叠写入、陈旧读集、返工量和未解决依赖；
- 取消、超时、故障恢复与重复执行的结果。

除总分外，报告每项任务与运行的方差、失败样本和成本；不能仅用某次成功演示或团队自生成的测试证明多 Agent 优于单 Agent。
