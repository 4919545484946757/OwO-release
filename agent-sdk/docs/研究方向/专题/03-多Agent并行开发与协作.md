# 多 Agent 并行开发与协作

## 需要比较的协作路线

| 路线 | 主要方法 | 关键资料 | 要测的代价 |
| --- | --- | --- | --- |
| 角色流程 | SOP、角色消息、阶段交接 | MetaGPT、ChatDev、AutoGen | 交接轮数、串行等待、信息丢失 |
| 异步隔离 | 中央计划、依赖图、独立 worktree、结构化集成 | CAID | 合并、验证、依赖同步成本 |
| 共享 Git | 同一工作区、动作可见性 | PASC | 写干扰、错误传播和协调成本 |
| 版本化共享状态 | 读版本、条件写入、陈旧状态识别 | STORM | 拒绝率、重试、锁与返工 |
| CRDT 共享编辑 | 文件合并、claim、状态与广播 | AgentRoom | 文本收敛后的语义集成成本 |
| 动态拓扑 | 按贡献/任务选择成员和通信方式 | DyLAN、扩展规律研究 | 路由、通信与额外模型调用 |

原始来源：[MetaGPT](https://arxiv.org/abs/2308.00352)、[ChatDev](https://arxiv.org/abs/2307.07924)、[CAID](https://arxiv.org/abs/2603.21489)、[PASC](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.18)、[STORM](https://arxiv.org/abs/2605.20563)、[AgentRoom](https://arxiv.org/abs/2608.23740)、[DyLAN](https://arxiv.org/abs/2310.02170)。论文任务、模型与预算不同，不据此给路线排名。

## 任务拆分先定义契约

一个开发节点应包含目标、范围、依赖、接口约定、验收方法、产物类型与集成基线。角色只是能力与限制配置。两个节点若都写同一共享接口，必须先协调接口版本或建立依赖；把它们同时派出并不自动创造独立性。

对于共享工作区，Worker 记录读版本或 read set，提交时验证关键依赖仍有效。写租约应绑定 run、task、attempt 和 epoch；取消或过期后拒绝提交。队友动作流只共享必要事实和变更，避免把全部对话重复灌入每个 Worker。

对于隔离 worktree，节点产物应包含 commit、变更范围、依赖基线和验证收据。中央集成核对依赖版本、处理合并、执行独立验收。Worker 自己测试通过只是节点证据，最终目标还要针对集成版本验证。

## 选择并行的依据

估计可独立子任务数、共享写入程度、依赖深度、验证成本和模型请求容量。可以先并行只读探索，再串行确认接口，随后按独立文件组并行实现。提高 Worker 数会同时增加上下文、请求等待、评审、返工和集成成本。

[扩展规律研究](https://arxiv.org/abs/2512.08296) 和 [MAST 失败分类](https://arxiv.org/abs/2503.13657) 提醒我们关注这些条件。对本项目的收益判断必须用同任务、同模型、同预算实验。

## 建议的对照实验

比较单 Agent、固定角色流水线、依赖驱动共享工作区、依赖驱动隔离 worktree。再分别移除队友动作摘要、版本校验和中央验收，测这些机制各自的贡献。记录成功率、墙钟、关键路径、等待、冲突、重复修改、返工、集成失败、模型用量和人工介入。

[AsynCodeBench](https://arxiv.org/abs/2609.32662) 可借鉴依赖检查与依赖解决时间；[CooperBench 源码](../研究资料库/project-notes/cooperbench--CooperBench/README.md) 用于冲突型任务参考。不要将“Worker 都返回成功”直接当作目标完成。
