# 工作流与持久化执行

## 三类机制分别承担什么

| 类型 | 主要问题 | 资料 |
| --- | --- | --- |
| 图状态编排 | 节点、边、状态更新、子图和中断 | LangGraph、Dify、CrewAI Flow |
| 持久化执行 | 崩溃恢复、历史重放、异步等待、重试和取消 | Temporal、Restate、Prefect |
| 业务自动化 | 定时或事件触发、外部连接、凭据和执行记录 | n8n、Dify、MCP Agent |

[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence) 区分 thread 的 checkpoint 与跨 thread 的 store。[Temporal 工作流文档](https://docs.temporal.io/workflows) 通过事件历史重放恢复执行，将外部操作放入 Activity。两种机制的运行方式不同，不能用“都存状态”概括。

## 建议的任务运行记录

每次运行绑定 run_id、输入摘要、定义版本和授权快照；每个节点绑定 task_id、attempt、依赖产物和状态版本。工具动作另记 operation_id、参数摘要、执行收据及外部结果引用。审批与人工输入是持久化事件，恢复时重新核对其有效性。

状态可以描述为 planned → ready → running → waiting/succeeded/failed/cancelled。waiting 必须注明是在等审批、用户、预算、租约还是外部任务，以及唤醒事件和截止条件。该状态图是建议设计，不是当前接口承诺。

## 恢复不意味着外部副作用只发生一次

节点在“工具写入成功、收据尚未落盘”时崩溃，重新执行可能重复写入。重试前应查询 operation_id 的结果或外部状态；支持幂等键的接口传递同一键。不可逆操作需要明确提交边界及失败后的恢复路径。仅保存聊天内容或节点 JSON 无法自动解决这个窗口。

并行节点还需要读版本与写范围。恢复后的旧 attempt 不能继续提交；审批撤销和取消要传到执行面。事件排序、状态更新与审计之间的事务边界应显式记录。

- [n8n](../研究资料库/project-notes/n8n-io--n8n/README.md)：workflow-execute 与 active-workflow-manager。
- [Restate](../研究资料库/project-notes/restatedev--sdk-typescript/README.md)、[Prefect](../研究资料库/project-notes/PrefectHQ--prefect/README.md)、[MCP Agent](../研究资料库/project-notes/lastmile-ai--mcp-agent/README.md)：持久化调用、任务生命周期和工具组合的对照。

## 研究验收案例

在模型调用后、工具提交后、状态提交前后分别中断进程，观察恢复后的最终文件、外部结果、状态和审计。另覆盖重复触发、取消后迟到回调、人工等待恢复、审批撤销和迁移旧定义。验收必须给出数据状态与可执行检查，不只看 API 返回成功。
