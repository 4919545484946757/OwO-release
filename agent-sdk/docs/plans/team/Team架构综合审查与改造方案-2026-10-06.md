# Team 架构综合审查与组织改造方案（2026-10-06）

## 审查结论

本次依据当前工作树 Rust 源码做静态审查，未运行 Cargo。Team 已有事件驱动 DAG、有界并发、写范围、租约/epoch、CAS Artifact、Reviewer 和 DeliveryGate，不能概括为“只是多个 Agent 并发”。但调度控制面仍有职责重叠与状态复制，当前架构尚不足以证明速度、资源和交付质量能稳定优于 Single。

## 源码事实与问题边界

1. `goal/mod.rs::run_inner` 使用 `ReadyFrontier` 和 `JoinSet`；完成节点会即时解锁后继并按关键路径排序。因此固定批次屏障不是当前主要缺陷。
2. `workswarm/coord_run.rs::run_phase` 领取/持久化 ready 节点，按依赖边构造仅含本阶段可达工作和成功依赖锚点的子图；`GoalRunner` 又在内存子状态中推进 DAG、attempt 和计数。协调器通过进度通道合并状态，阶段结束再合并结果、重算 ready。epoch/attempt 有防过期保护，但两份可变状态仍要保持一致。
3. 同一运行入口周边同时处理角色跳过、子图构造、取消、进度落盘、终态合并、评审返修和 Human 门闩。创建期策略已经拆到 `coord_strategy.rs`，任务画像已拆到 `task_profile.rs`；运行期仍是多职责协调器。
4. 每个 `RoleWorker::run` 都调用 `assemble_context_slice`。它重读 Team/ProjectSpace/Goal、角色元数据、Artifact Catalog、共享事实、ChangeSet 与 CAS 预览；同阶段并行 worker 会重复获取团队级上下文。优化需按 epoch/revision 缓存基础快照，同时允许后继读取新完成的 Artifact。
5. 项目已有分层遥测：Server 记录 `registry_build`、`phase_orchestration`、`delivery_finalize` 生命周期 span；Worker span 按 epoch 汇总 wall/provider wait/model calls/tokens/budget wait/lease wait，并有阶段面板。Worker wall 原先无法区分上下文组装。`team.context.assembled` 无内容事件已接入 /metrics 与诊断聚合，按角色和 phase epoch 输出 P50/P90、失败数。Worker 结束时从协调器内最多 4096 条的一次性 HashMap 按完整身份 O(1) 取出时长，并将结果写入现有 Worker JSONL span；审计事件仍保留作人工诊断，不再参与 Worker 收尾扫描；索引淘汰的极端样本显式计入未归因。旧 span 没有该字段时计入 `attribution_missing_count`。WorkSwarm 面板说明这是 Worker 内部耗时且不与墙钟相加。模型/工具、产物登记、DAG ready wait 和状态持久化仍未分别计时；Rust 聚合和 API 集成测试尚未运行。
6. 这些额外角色、规划、上下文、评审/返修与集成成本解释了窄任务上 Team 为何可能更慢；当前源码没有证明哪一项占比最大。安全和验收门禁不能为提速而弱化。

## 目标组织架构

目标是“一个状态权威者，多个专责执行面”，不是继续增加 Agent 角色：

```text
CLI/API → Team Facade + Benefit/Risk Policy → PlanCompiler
        → Durable Run Scheduler ↔ RunStore/EventLog
        → bounded Worker Executor → CAS Artifact/Context Store
        → Validation Lane → Accepted / Rejected / NeedsHuman
```

- **Team Facade / PlanCompiler**：解析请求、做收益/风险路由、编译并校验不可变 DAG、分配预算。Auto 模式只有在配对收益证据、可并行宽度和质量要求支持时组队；否则 Single。显式 Team 保持用户所选拓扑，但清楚呈现开销。
- **Durable Run Scheduler**：成为 readiness、attempt、租约、epoch、并发配额、重试和预算的唯一事实源。Worker 接收带 run/step/attempt/epoch 的 claim，完成后只发事件；不再由 Team coordinator 与 GoalRunner 各自复制一份可推进状态。Single 与 Team 共用状态转移、取消/恢复和完成判定，Team 只提供 DAG 与策略。
- **Worker Executor Pool**：只负责有界派发、模型/工具生命周期、取消和用量采集，不改 DAG。关键路径后继由 Scheduler 收到完成事件后即时派发。
- **Artifact & Context Store**：按 CAS ref/version 流转产物。每个 epoch 建团队只读基础上下文快照，同阶段 Worker 复用；按 step 追加已完成依赖的 Artifact。缓存键含 team、epoch、revision 和 scope，replace/retry 时失效。
- **Validation Lane**：局部验证、独立 Reviewer、责任人返修 DAG 和 DeliveryGate 为显式状态转换。返修使旧回执失效，Reviewer 必须检查最后一次写入之后的源码快照；由宿主证据决定接受。
- **Telemetry / Policy Controller**：区分 Lead/策略、队列等待、上下文、模型、工具、状态持久化、Review、返修、集成、验收时延；记录每阶段 token、请求、工具调用、重试和质量。绑定一致的配对评测未达到质量与资源护栏时，Auto 默认 Single。

## 改造顺序

**P0 指标贯通**：复用现有 phase/Worker span 和面板，不另造重复生命周期系统。上下文装配时长现由协调器内最多 4096 条的有界 O(1) 索引按完整执行身份归因，再持久到 Worker JSONL 并按角色和 epoch 展示；审计流不在完成路径上被反向扫描，历史 span 的缺失归因会显式计数。下一步分别量化 DAG ready wait、状态持久化、模型/工具、产物登记和交付返修。总时长与并行 Worker 内部耗时必须分别展示，不能把重叠 span 相加冒充墙钟。不得为观测额外调用模型；持久数据有界且脱敏。

**P1 统一状态所有权**：定义 `RunCommand`（claim/cancel/retry/accept/reject）和 `RunEvent`（claimed/started/completed/failed/reviewed）；一个状态转移入口校验 epoch/attempt/租约并持久化。分步迁移，不同时重写权限和调度算法。验证并发解锁、重复事件幂等、取消收尾、崩溃恢复、Human 恢复和返修回执失效。

**P2 上下文快照**：先复用稳定团队信息，再附每 step 的依赖 Artifact；验证后继读到新产物、重试不读过期产物、并发 worker 的基础快照版本一致。

**P3 自适应拓扑**：使用已验证收益、DAG 并行宽度、写冲突、额外模型调用与质量风险作策略理由；LLM 自报 effort 不能独立构成组队收益证据。

**P4 成对评测**：同模型/任务集/策略版本测中位数与 P95 墙钟、通过率、盲评质量、token、模型/工具调用、返修率和独立 case 置信区间。代码静态检查和模拟不能替代真实模型比较。

源码能确认存在阶段子状态复制与重复上下文装配路径；现有生命周期/Worker 指标给出阶段和请求层基线，上下文事件已能在 metrics API 和 Team 面板按角色/epoch比较，但这仍不证明该成本主导真实任务耗时。本轮新增的 phase_subplan.rs 从 ready frontier 沿反向依赖边一次性推进可达工作，并只带直接成功依赖锚点；构图扫描复杂度为 O(V+E)，避免旧式多轮全图固定点扫描在反向拓扑顺序下退化到 O(V²)，也避免每阶段携带全部历史成功节点。并行 Worker 的依赖 Artifact 预览现在通过协调器共享的内容寻址缓存复用，只缓存已由 CAS 校验的不可变页，容量上限为 32 MiB/4096 键，并通过有界每键 single-flight 合并并发冷读，命中时复核声明大小；这减少同一不可变依赖的重复 IO，但缓存命中收益尚无运行指标。TeamContextRead 对带 file_hash 的工作区事实改为 blocking pool 流式哈希，64 KiB 缓冲且单文件最多 64 MiB；超限、I/O 失败或 join 失败均不把事实作为新鲜内容注入模型上下文。该上限行为有源码和单测覆盖，尚未通过 Rust 测试运行验证。以上性能收益仍缺运行指标。按用户要求本轮先继续静态检查，未启动 Cargo；类型检查、Rust 测试、真实请求遥测和成对评测仍待后续验证。


## 预算准入与阶段继承修复（2026-10-06）

静态调用链审查确认 GoalRunner 的预算并非可靠的并发准入控制：旧代码把 attempts 全额记为 retries；预算只在步骤结果合并后检查，导致首次执行也会消耗重试额度、max_total_retries=0 会阻止首个请求，并允许并发 Worker 在合并计数前越过 max_steps/max_total_retries。Team 每阶段又创建计数为零的子状态，若不显式携带主状态的已用量，阶段切换会重置预算。

现已在 goal/execution.rs 增加共享 ExecutionBudget。每次 Worker 首次调用、步内重试和 critic 作者修订都在执行前用短时 Mutex 事务预留全局步骤与重试额度，锁不跨 await；只有首个调用不扣 retry。GoalRunner 删除基于合并快照的前置熔断，避免额度刚好用尽的已完成计划被误判失败。Team phase runner 使用持久主状态的 base_steps_taken/base_total_retries 初始化账本，避免跨 phase 重置。结果合并保留 steps_taken += attempts，并按 attempts - 1 统计本 StepOutcome 内的重试；replan 次数仍由独立 max_replans 管理。

新增回归覆盖：首次调用在 max_total_retries=0 且 max_steps=1 时可成功；重试额度为零时只执行一次失败调用；并发三任务在 max_steps=2 时最多触发两个 Worker 调用；Team phase 继承此前阶段用量；以及 StepOutcome 的 steps/retries 计数。该 ledger 是运行内的并发准入器，GoalRunState 仍提供恢复基线和持久计数，尚未消除 Team phase 子状态复制。

本轮只做静态验证：相关四个 Rust 文件通过 rustfmt 检查，scoped git diff --check 通过（保留仓库现有 CRLF 规范化提示）；Rust 测试、Cargo 类型检查、真实 Team 运行和 Single/Team 配对 benchmark 尚未运行。当前结论是预算并发门禁的源码路径已调整，不宣称运行时回归通过或速度、token、交付质量已有量化改善。

此外，GoalRunner 原先静默丢弃状态检查点写入错误，可能在内存状态已成功、恢复状态未落盘时仍返回成功。现在会保留最近一次检查点错误；运行开始时尝试恢复写入，运行结束仍未成功则向调用方返回明确错误，错误同时进入 Goal 事件与审计。若期间后续检查点成功，则错误清除，因为最新状态已成功发布。新增将 persist_dir 指向普通文件的回归测试，验证不能把内存成功冒充为可恢复的成功。该修改目前仅做源码与格式静态检查，尚未由 Rust 测试或类型检查确认。


## 进度合并 attempt fencing 修复（2026-10-06）

Team 进度批次原来只验证整体 phase epoch；同一 epoch 内若 step attempt 已被重新领取或重置，迟到的旧快照仍可能覆盖新 attempt 的状态、产物和计数，并产生过期的动态跳过事件。现在进度合并要求当前 StepRecord 与快照的 phase_epoch、attempt_id 同时一致；未知 step 与身份不匹配更新整条丢弃，预算计数和 skip 事件也不会从 stale snapshot 进入持久状态。新增回归测试验证旧 attempt 的 Failed 状态、产物、计数和 skip 不污染当前 Running attempt。仅完成静态源码与 rustfmt 验证，Rust 测试仍未运行。

## Team attempt 准入持久化与剩余边界（2026-10-06）

Team 的 GoalRunner 现通过有界 attempt-admission 通道请求宿主确认。持久准入事务集中在 workswarm/coord_admission.rs，阶段循环只负责接收请求、取消处理和调度。每次 Worker 调用或 critic 作者修订先预留本地并发预算，再由 TeamCoordinator 校验当前 phase_epoch/attempt_id，在一把 Team 锁内合并准入批次、增加 steps_taken/total_retries/StepRecord.attempts 并原子写 GoalRunState；只有检查点成功后才确认请求并允许调用继续。持久化失败时请求失败关闭，不会启动 Worker；若检查点成功后进程在确认或调用前崩溃，预算按已预留计数保守消耗，恢复后不会重置。进度合并和阶段最终合并保留已持久化计数与单调 attempt 数。workswarm/coord_progress.rs 负责 attempt-fenced 快照合并、持久化和跳过审计；coord_run.rs 只驱动阶段选择、取消与执行收尾。

新增的纯状态测试覆盖计数、重试和旧 attempt 拒绝；Goal 执行测试覆盖宿主拒绝准入时 Worker 调用次数为零；通道测试覆盖调用方必须等待宿主确认。这些 Rust 测试目前尚未执行。单独使用 GoalRunner 且未附加持久准入宿主时，预留仍只在进程内生效；统一 Durable Run Scheduler、跨 Single/Team 的唯一状态转移和真实故障恢复验收仍未完成。Team provider 请求账本仍负责细粒度请求/token 预算，两类预算相互补充。



## 取消信号与准入确认竞态修复（2026-10-06）

旧路径先持久化并确认 Worker attempt，再由 tokio::select! 处理取消并设置 GoalRunner abort；取消 watch 已触发而 select 尚未轮到取消分支时，准入确认可能先唤醒 Worker。现在 CancelToken 自带共享 AtomicBool，cancel() 先设置它再通知 watch，run_phase 在启动 GoalRunner 前绑定同一 abort flag。StepRuntime 在等待持久准入返回后、Worker 调用前检查该 flag，避免取消已生效后启动新模型/工具请求。在飞 Worker 仍依赖现有协作式 abort 与有界清理。回归测试源码覆盖 CancelToken 原子标志及 GoalRunner 信号共享；Cargo 类型检查和 Rust 测试因资源门槛尚未运行。

## 阶段状态投影与预算计数权威（2026-10-08）

最新静态追踪发现，阶段状态合并函数同时处理 StepRecord 投影和预算计数增量，而阶段收尾又以持久准入高水位/阶段基线重算计数。最终高水位赋值可以保护本路径，但通用合并副作用让状态权威不清晰。现已将 merge_phase_records_into_full 限定为合并阶段步骤记录与 Goal 错误，不再改 steps_taken 或 total_retries；coord_finalize.rs 显式以 durable admission high-water 和 phase baseline 计算总计数，并保留已持久化 attempt 高水位。新增测试覆盖 phase projection 不可改写 durable budget counters。

该改动通过相关 rustfmt --check 与 git diff --check 最终复核。Cargo 编译和 Rust 测试受当前环境门槛阻止：可用物理内存约 5.99 GB、使用率 81.1%，T 盘可用约 4.93 GB。它明确了预算账本唯一写入边界，但 GoalRunner 与 Team 仍各自维护阶段内和完整步骤记录；统一状态所有权及 Single/Team 成对评测仍是未完成的核心工作。


## Team phase projection 的 attempt 身份栅栏（2026-10-08）

阶段最终合并此前只依赖 run-wide epoch，纯状态 reducer 未按 StepRecord 的 attempt 身份拒绝旧投影。现要求 phase snapshot 与 durable record 的 epoch 均等于 `GoalRunState.execution_epoch`，且 `attempt_id` 相同；成功记录仍不可回退，runner 投影仍不能修改准入预算。这样把 progress merge 已有的 `phase_epoch + attempt_id` 防护扩展到了 phase finalization 的逐步骤状态投影。

验证：rustfmt 检查通过；Core 中匹配 phase projection 的 3 个单测通过（包含旧 attempt 拒绝、当前 attempt 合并及预算高水位）；WorkSwarm 主集成测试和恢复测试均退出 0，恢复为 8/8。当前只证明状态投影契约，不代表 Durable Run Scheduler 已统一，也没有真实模型配对、提速或 Token 下降证据。后续仍需把目标状态权威从 GoalRunner/Team phase 双份可变记录收敛到一个 durable scheduler，并在迁移中保留 claim、取消、恢复、Human 与返修语义。
