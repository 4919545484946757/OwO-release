# 媒体执行链路与失败落盘整改

日期：2026-10-27。基线为 GitHub 检查点 21d64098；当前增量尚未提交。对应原审查 F2 / F9，并补充 F10 主会话执行侧的证据，不代表团队任务租约链路完成。

## 已复现的问题与修复

原生回归使用实际 Daemon 路由、ToolHost、一次性审批、内置 generate_image / text_to_speech、宿主命名连接、Artifact/CAS 与会话存储。模型输出和媒体 HTTP 对端为隔离的确定性夹具，不调用云端。

此前媒体工具先保存响应字节，Server 发布器才检查格式。HTTP 200 返回普通文本时，工具最终报告失败，但原始文件已经占用了请求的输出路径；重试因此被拒绝覆盖。原先的失败分支测试实际确认了这一落盘行为。新增 invalid_builtin_media_is_rejected_before_file_commit_and_can_retry 在修复前原生执行 exit=101，失败点为 generate_image 的失败输出仍然存在；并非仅靠源码推断。

现在 Core 执行、内联预览和 Server 发布器复用同一个 media_output_mime 文件头识别函数。图片和语音在最终写入之前拒绝无法识别的内容，返回 media/invalid_content；无需删除用户文件或放宽拒绝覆盖规则，后续可在同一目标路径重试。审批、取消、网络开关、输出范围、CAS、发布和鉴权入口保持原有链路。另修复 CLI 工作流自动选择处的布尔比较静态检查错误，保持选择语义。

该识别沿用原发布器支持的格式，是有界文件头判断，不是完整解码器。带合法头但内部损坏的内容、音频 codec/请求格式匹配，以及有效文件写入后数据库/CAS 发布失败的恢复，仍需独立处理；本批不宣称所有失败都具有文件与数据库的原子性。

## 覆盖的实际链路

新增 media_execution_api_tests.rs：

- PNG 和 PCM WAV 各验证 2 KiB、100 KiB、1 MiB。经真实 HTTP 审批后调用各自命名端点，核对实际请求模型；输出文件、摘要、字节数、MIME、结构化 SSE 引用及持久历史一致，大媒体字节不进入 SSE。
- 重新构建同一隔离数据根的宿主，鉴权读取保存的产物；核对完整字节、Range 206、无 token 401 及旧启动 token 401。没有将单纯目录或配置返回 200 当成媒体执行证据。
- 拒绝审批时不访问媒体端点，不落输出文件。上游 HTTP 503、无法识别的内容及响应体停滞后按精确 turn_id 取消，不发布成功输出。
- 无法识别的图片与音频不占用目标文件；同一会话、同一路径换成有效响应后可以再次审批并生成产物。

夹具运行在独立测试子进程，关闭模型云端出境；媒体端点仅为 127.0.0.1，凭据不从用户环境带入。这里核对的是无凭据的本机命名连接与独立模型路由，不扩大为远端鉴权或桌面保险库验证。
