# Single / Team 15 分钟实测记录（2026-10-08）

## 结果

评测使用同一模型 glm-5.3-flash、同一任务和任务级 64 次调用额度；Single 与 Team 共享每任务 900 秒超时。预定 15 个不同任务（14 个 Python 代码修复、1 个研究任务），每项重复 2 次，共 30 个配对重复 / 60 个执行格。达到用户限定的 15 分钟后停止。最终落盘 3/60 个执行格：一组完整配对和第二次 Single；另有一个 Team 重复已开始但未落盘。没有生成完整配对报告，样本只作方向性观察。

## 低调用额度复现

同一任务另一次以任务级 7 次调用上限配对：Single 46.470 秒、5 次模型调用、5 次工具调用、7,402 tokens，检查 6/8；Team 73.816 秒、7 次模型调用、9 次工具调用，预算耗尽、没有交付物，token usage 未知。Team 约慢 1.59 倍。证据：scratch-eval-runs/team-single-paired/pilot-15m-20261008-201417/matrix/state.jsonl。

## 根因与改进方向

1. 仅修改 suite 默认调用上限无效：任务文件自己的 max_model_calls 会覆盖默认值。本轮发现并同步了候选任务级上限。
2. 高额度 TeamRun 的策略快照计划 builder、critic、leader 三个预算槽，总预算 9，但 code-change-v2 实际只组 implementer 与 reviewer；两处拓扑与预算契约仍不一致。
3. 提高额度后 implementer 使用 17 次模型调用，reviewer 使用 7 次；Team 总耗时 390.6 秒，交付检查仍失败。增加调用额度没有带来质量优势。
4. 需要让模板角色、策略计划、角色轮数和全队共享预算由同一份执行计划产生；修复失败后将宿主检查结果回交唯一写者，采用有界返工并复验；模型调用数和 Token usage 要按角色完整归集。
5. 先用契约测试保证预算计划与执行拓扑一致，再运行完整冻结任务集配对。当前 n=1 的完整高额度配对不能支持普遍性或统计结论，也不能宣称 Team 已稳定交付。

## 实现与验证状态

- 新增 code-change-v2：实现者单写、完成后由只读审查者评审；旧 v1 模板保留。
- 将 v2 实现者和审查者的模板回合额度设为 16；候选评测套件任务级额度设为 64、任务超时设为 900 秒。
- Core 模板测试 11/11、ProductEval Team 执行器测试 25/25，以及 ProductEval all-targets cargo check exit 0，均在最后一次角色额度改动之前通过。之后 live harness 重新编译了当前 Core/ProductEval 代码并实际运行。
- 15 分钟 live harness 在截止时被中断，退出码 1，完整配对报告未生成。cargo fmt --all -- --check 曾失败，格式门禁未重新通过。
