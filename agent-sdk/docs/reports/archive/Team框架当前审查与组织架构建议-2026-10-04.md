## 合理基础

- TeamCoordinator → GoalRunner 已有依赖图、JoinSet 和并发上限；run_phase 的领取/合并用短锁，Worker 在锁外执行。就绪后继不必等慢兄弟，定向测试通过。
- 工具能力和写范围按任务、角色、工作区取交集；写租约覆盖前快照、执行、后快照和 ChangeSet 登记。保留权限、取消、审计与过期结果拒绝。
- ProjectSpace/CAS、版本化 Artifact 和 revision/CAS 共享事实能实现可追溯交接。
- DeliveryGate 检查产物、ChangeSet、验证回执、独立评审和最终文件版本；模型自报 done 不等于交付。
- Prompt 已有上游字节预算/截断记录，WorkerRuntime 共用执行与格式修复计数；评审可把问题派回原 owner，有限次返修。

## 关键问题

### P0：首次 TaskGraph 执行身份冲突

coord_accessors.rs:141 的 phase_epoch 缺省返回 0。coord_run.rs:909 正常领取时直接使用它；task_context.rs:199 却拒绝 phase_epoch=0。bump_phase_epoch 只在 steer/返修接管路径调用，正常首次派发没有初始化。

这是确定的源码契约冲突，会使首次 TaskGraph Worker 在 validate_runtime_binding 被拒绝，与三个并行失败的路径吻合。本次未捕获每个步骤的完整 error，不能断言所有失败只有此原因。

解决：由宿主统一领取、持久化 run/task/step/attempt/epoch，首次合法代次从 1 开始，恢复单调推进；不要放宽 Worker 非零检查。接管代次和步骤尝试次数分别管理。

### P1：自动策略缺少真实任务画像

coord_run.rs:202 的 TaskProfile 固定单产物、零输入、普通风险、无历史成功率。收益 gate 防止无证据自动 Team，但不等于能分析可并行性。显式角色/模板保留规则也使策略标签与实际拓扑可能不同。

解决：根据任务图提取独立宽度、关键路径、冲突范围、共享接口、验证成本；输出实际执行者、评审和验证任务及预算。明确区分“一个执行者加评审”和“多个执行者”。

### P1：验证/评审仍附着在角色流水线

自动 reviewer 默认依赖所有角色，容易形成尾部等待。生产 run_command 仍来自 Worker 工具面，能力映射还与文件写能力条件绑定。已有可选集成跳过逻辑，应保留，但不能据此认定独立验证队列已完成。

解决：建立 ValidationLane，执行宿主授权的确定性检查；Reviewer 只读指定候选版本和证据。命令可能产生副作用，仍须经 ToolHost、策略、资源与范围限制。允许局部检查提前运行，最终针对统一候选版本重查。

### P1：Single/Team 统一尚不完整

已共用 completion DTO、部分判定及 command_evidence，但生命周期、持久化与证据组装仍分开。共用结构体不能证明两条路径有一致交付行为。

解决：收敛 ExecutionContext、CandidateVersion、EvidenceLedger、AcceptanceService。Single 是同一执行内核中的一个执行者；客户端和评测复用生产验收入口。

### P2：租约和上下文成本需要实测

生产写租约覆盖整个 Worker 尝试，冲突范围可能连同模型思考一起串行。摘要预算已有实现，关键接口和验收条件仍应独立传递。

解决：测 lease_wait、模型等待、上下文/schema 字节、重复读文件、验证等待；有证据再改租约粒度。冲突范围隔离候选分支或串行，同文件保持单 owner。

## 推荐组织架构

用户请求 → Coordinator → TaskGraph → WorkerPool → Candidate/ChangeSet
                                                ↓
                             ValidationLane + ReadOnly Review
                                                ↓
                              AcceptanceService / DeliveryGate
                                     ↓                 ↓
                                  Accepted          原 owner 返修

Coordinator 是宿主控制器，负责需求绑定、任务图合法性、身份、资源预算、恢复与最终状态。拆分不明确时才调用模型规划，不固定创建 planner/leader/integrator 三个常驻模型角色。

WorkerPool 是执行容量，不是固定岗位流水线。每个任务有明确 owner、读参考、写范围、接口、验收计划和调用预算。先以 1～2 个写执行者组织，在证明独立且有收益后扩容。

EvidenceLedger 保存需求、版本、命令、评审和问题的绑定。后续相关改动使旧证据 stale。缺失 usage 保持未知，不报零成本。

ValidationLane 合并同版本重复检查，分别限制模型请求、验证命令和构建资源。Review 针对候选版本；返修按依赖范围失效/重验，避免整队重做。

AcceptanceService 统一交付判定。文本结束、Worker done、步骤成功不能替代 Accepted。

## 实施优先级与验收

1. 修复首次 epoch/恢复契约，追踪三个并行失败和一个交付失败；校正策略测试职责读取。不得放宽交付门。
2. 统一运行身份、候选版本、证据与验收入口。
3. 建立独立验证队列，减少尾部模型角色、重复命令和无必要集成。
4. 从真实任务图生成策略，再做冻结同源、同模型、同需求、同检查器的重复配对评测。

稳定验收必须覆盖真实 CLI/Daemon 入口、写文件、命令、交付、返修、取消、重启恢复、旧证据拒绝和客户端状态。随后比较总耗时、成功率、回归、模型/工具调用与 token 的分布；先冻结合格阈值，不靠某一轮多通过一项宣布 Team 优势。

当前建议保留架构做收敛式重构；不能称为稳定生产能力，增加 Agent 数量也不是优先解法。

## 2026-10-05 Team 预算接线修复

继续检查策略决策到生产 Worker 的实际调用链后，发现一个直接放大耗时与 token 的断层：策略决策会展示 producer/critic/leader 的预算，例如 4+2+3；但 Server 构建 Worker 时只从模板描述读取角色预算。没有模板的动态 Team 会把预算读成 0，WorkerProfile 随后回退到默认 12 轮。若没有单独设置全队 max_model_calls，这一默认值可能让实际模型调用显著超过策略展示值。

现在创建阶段把缺失的动态角色预算按 producer、critic、leader/integrator 职责绑定到 RunMeta；模板显式预算仍优先。Server Worker 构建优先使用同一份 RunMeta 预算，模板预算只作为兼容回退。新增回归源码覆盖动态角色预算、Reviewer/Integrator 映射、模板预算优先级及 Server 对 RunMeta 的优先读取。

本次只完成源码静态修复。尚未编译或运行新增测试，也没有检查已创建团队的历史 sidecar 是否补齐预算；旧 RunMeta 或非本创建入口可能仍无该字段，Server 将按模板预算回退，最终再到 Worker 默认值。真实 Worker 调用数、token、耗时变化均未测量，因此这只能说明减少预算漂移的实现已接通，不能声称已测得更快或更省。证据见 docs/qa/evidence/team-role-budget-consistency-20261005.json。

## 2026-10-05 Goal 进度队列合并

Team 执行期间，GoalRunner 先前把每个步骤状态变化连同完整 StepRecord 放进无界 channel，Server 逐条持久化。模型与存储速度不匹配时，同一任务可能排入多个重复快照。现在换成单槽有界唤醒与按 step_id 合并的 pending 快照；一次批次只持一次 Team 锁、读取一次运行状态，并在存在变化时落盘一次。批处理用最大观察值维护步骤与重试计数，StepRecord 对比覆盖 attempt_id、epoch 与验证回执，因此 receipt-only 更新也能触发持久化。跳过原因仍从更新或最新 StepRecord 取回。

该设计减少重复快照和队列唤醒；pending 仍与本阶段唯一任务数成正比，不是全任务图内存硬上限。源码新增同步骤快照合并与 progress reducer 测试，但按用户要求未编译、未运行测试，也未压测慢存储、取消及恢复。不能据此量化速度或质量改善。后续需重点验证取消期间 drain、skip 事件和阶段完整状态合并。

## 2026-10-05 Single / Team 完成记录持久化对齐

检查后发现除 Team 与 Single 的入口不同外，Single 内部也存在两个实现：Trace 已绑定 ResolvedTaskContext 并收集 attempt 相关的历史 Accepted 写入；新加的 Session helper 却只按 session_id/当前 turn 与当前写收据计算候选。两种记录并行会使 UI 的 TurnStats 与诊断 Trace 对同一回合给出不同证据。错误回合也只有 Trace 保存结果。

现已删除重复 helper，提升 Trace 的宿主记录生成器为 Single 唯一实现；正常回合、Trace 与 Session 共用它。失败/取消时服务端从 Trace 回填 Session 并向 `TurnFailed` 透传可选记录。SQLite v9 持久化 Session 最近一回合记录，fork 不继承父记录。失败验证仍保留作诊断证据，但不会混入 Accepted 的证据集合。单一候选快照哈希仍使用 Single schema，与 Team 的 Artifact + workspace 候选域不同。

新增或扩展回归源码覆盖 accepted 收据过滤、历史候选绑定、SQLite 往返/fork 隔离、协议旧版兼容与失败记录往返、TypeScript 终态事件透传。按要求未编译、未运行测试或迁移；桌面没有展示明细，Session 只存最近记录。源码证据见 `docs/qa/evidence/single-team-completion-record-20261005.json`。


## 2026-10-05 动态 Team 串行拓扑收敛

静态调用链显示：无模板、无显式 roles 的 Team 默认生成 `planner → builder → critic → leader`；策略预算则按 producer/critic/leader 展示。planner 会额外占一个串行模型阶段，未列入策略的角色可能回退到 Worker 默认 12 轮；leader 又被画像计作第二个“预期 Artifact”，形成由 integrator 自身触发 integrator 的循环信号。

已对动态默认 Team 做策略投影：producer + critic 是显式 Team 的基本链；只有多来源或多真实交付角色才增加 leader。删除 planner 等未计划角色时，DAG 依赖沿被删除节点回接到最近的保留上游，producer 按任务类别更名并迁移预算。裁剪记录包含声明预算，预算缺失时按 Worker 实际默认上限计入 saved_budget_calls。模板和显式 roles 不改写。
