# ADR 0028：候选刷新优先级与失败恢复

- 状态：P3 后体验优化已采用；修订 ADR 0026 的超时快照语义
- 日期：2026-08-03

## 背景

选择 `ni'hao'shi'jie` 中的“你好”后，TSF 能正确提交词语、删除 `ni'hao` 并将预览改为 `shi'jie`，但候选列表可能仍停在整句的视觉快照且无法交互。初始实现对所有 Core 请求共用 100ms 上限，并在失败时直接丢弃结果，UI 的 `candidate_request_pending` 没有终态。增加失败终态后进一步确认：Core 进程始终存活，`shijie` 和 `shi'jie` 只需 9～13ms；真正的传输竞态是 Core 在每个客户端后关闭旧命名管道实例、再创建新实例，连续请求正好落入中间空档时 `WaitNamedPipeW` 会立即返回 `ERROR_FILE_NOT_FOUND`。旧客户端将该瞬时状态误判为 Core 永久离线。部分提交后先唤醒学习反馈的顺序还会扩大该竞态。

## 决策

1. 部分提交成功后，主线程先裁剪拼音、发布剩余拼音的候选请求，再发布提交学习反馈，避免反馈的提前唤醒抢占管道。后台队列同时存在两者时仍先处理最新候选请求。学习反馈继续保序且不丢失，但不能阻塞用户可见的刷新。
2. Core 候选传输保持异步，单次上限从 100ms 放宽到 500ms。这不会延迟正常响应，只为完整词库首次访问、进程调度和管道建立留出边界。非关键学习反馈仍保持 100ms 上限。
3. 通用命名管道客户端在原截止时间内重试 `ERROR_FILE_NOT_FOUND` 和 `ERROR_PIPE_BUSY`：前者覆盖服务端更换实例的短暂空档，后者覆盖 `WaitNamedPipeW` 与 `CreateFileW` 之间被其他客户端抢占的竞态。截止时间到达后仍返回明确超时，不无界等待。
4. 候选传输失败、协议无效、request ID 不匹配或响应类型错误时，工作线程向 UI 投递与原 request、generation 和 page 对齐的失败终态及详细原因。旧请求的失败仍按现有世代校验丢弃。
5. UI 首次收到当前请求失败时，使用新 request ID 自动重试一次，不无限重试。第二次仍失败才清除视觉快照的候选文本与消费范围、结束 pending，并显示具体管道或协议错误。不得继续显示与当前拼音不匹配的旧候选。
6. 新增进程内真实管道回归：服务端处理第一个请求后关闭实例，故意等待 40ms 再创建第二个实例；第二个客户端必须在同一次 `exchange` 中跨过空档并获得正确响应。

## 结果

“你好”部分提交后，`shi'jie` 的候选请求立即越过学习反馈，并能跨过 Core 命名管道实例更换空档。即使 Core 确实不可用或响应损坏，候选窗也会进入明确终态，不再永久保留旧整句候选并锁住交互。

## 边界

- 500ms 是传输失败上限，不是候选性能目标；引擎 Release 基准仍以低毫秒级为目标。
- TSF 只自动重试一次。新的字母、退格或分隔符会发起新世代请求；Escape 仍可取消当前组合。

## 回滚

恢复反馈先发顺序和共用 100ms 传输上限，移除管道实例空档重试、UI 有界重试、失败终态与错误文案。该回滚会重新引入连续请求的瞬时断管和永久 pending，不改变 Core 协议。
