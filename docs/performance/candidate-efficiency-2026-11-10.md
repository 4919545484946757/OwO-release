# 候选链路效率优化：第一轮

日期：2026-11-10—2026-11-11（跨日完成）。优化前基线：`fabe5f2`（0.3.0）。本次是开发版更新；原有 0.3.0 安装包未覆盖，也未上传新包。

## 已实现

1. 模型元数据按需准备：关闭/缺失模型、基础结果仍待精化、已经模型排序的快照、非首页、双声母专用路径、取消请求等不再构造无用的模型候选池、置信信息、隐藏项副本和模型专用词频偏好。
2. 直接保留来源索引：切页及召回隐藏候选时同时保存原始候选行号，后续模型元数据按行号读取，不再为每个返回项重复遍历整个候选池，也不需要逐项创建字符串哈希键。
3. libime 批量复用前文：同一批候选只解析一次上下文，候选评分和两类校准复用相同的初始 LM 状态；不同请求之间不保留应用上下文。
4. 过期模型等待可取消：更新请求沿用原有命名取消事件，以最长 2 ms 的等待片段检查取消；总预算仍为 `min(model_timeout, 60 ms)`。新输入触发取消后删除旧发布映射，不再占用整个旧等待预算。
5. 调试页增加 `model_prepare_us` 子阶段和 `model_prepared` 标记，便于确认跳过的准备工作；取消等待通过 `model_wait_cancelled` 事件观察。

没有缩小分割/候选搜索预算，没有改词典权重、分区配额、候选限制或 LM 校准规则；候选 IPC 格式与 libime ABI 均不变。符号投影用到的原拼音片段仍独立保存，不能随模型元数据一起跳过。

取消的是旧请求的等待与发布，不是强制中断已经进入 libime 的原生计算。Core 主服务仍串行，大词库热更新和首次复杂纠错尚未在本轮重构。

## 本机隔离测量

两版使用同一份 v2 词典、同一份 `zh_CN.lm` 和相同的 libIMECore DLL；合成输入、空白用户词频、私有管道和独立配置目录，不连接日常 Core，不调用网络 API，不开启用户环境的计时采集。

### Core

8 个输入：`nihao`、`nipingchangyong`、`gongnnegjiekou`、`xianzaide`、`rgs`、`xiufuleisiwt`、`butianjia`、`baoliudangqiangaidongbingdabaoshangchuan`。

每版本每组 75 次，额外 5 次预热，按旧→新→新→旧的 ABBA 顺序执行；统计期间没有并行构建。页长 7、分区开启、模型关闭。以下为 8 个输入 × 2 轮的“各组 P50 算术均值”，不是合并全部样本后的全局 P50。

| 请求类型 | 旧版 μs | 新版 μs | 降幅 |
| --- | ---: | ---: | ---: |
| 未命中结果缓存 | 11597.33 | 11491.20 | 0.9% |
| 热首页 | 92.19 | 74.59 | 19.1% |
| 热第二页 | 84.71 | 69.09 | 18.4% |
| 预热后展开 | 126.07 | 74.57 | 40.9% |

未命中缓存通过不同的合成 context 区分缓存身份；不是断电后的冷启动或冷磁盘。Core 探针不走 TSF、材质绘制或符号兼容编排，因此不能把此表当作按键到屏幕的端到端收益。默认符号兼容链路由单独合同验证，不伪称已测得同样百分比。

64 组最终响应指纹一致：候选文字、消耗范围、分区序列、拼音预览及 `has_more` 一致；每组内也核对重复请求的稳定性。

首次复杂解析并没有显示可靠的大幅提升：约 1% 的均值变化不足以支持“首次输入已显著加速”。早期试测还出现过约 1% 的相反波动。热请求绝对值较小，仍受系统调度和设备负载影响。

原始记录：`build/candidate-efficiency-20261110/verified-before-{a,b}.jsonl`、`verified-after-{a,b}.jsonl`。较早的 `core-*`、`final-*` 属于探索数据，部分与构建并行，不作为上表依据。

### libime

旧/新 DLL 在同一进程中加载，保持模型与依赖相同。12 组“前文 × 候选池”交替测试顺序，每组 10 次预热、100 次测量。

- 空前文：基本不变。
- 21 字前文、16 候选：P50 从 243.2 μs 降至 23.1 μs，约下降 90.5%；P95 从 310.8 μs 降至 48.5 μs。
- 同样前文、其他三组 6 候选池：P50 约下降 70%–77%。
- 旧/新 DLL 相同接口的 204 次分数对比逐位一致，包含无前文、短前文、长前文以及尾字、句首和句中单字校准样例。比较的是“批量对批量、单条对单条”，不要求经过校准的批量分值等于标量分值。

这是单次模型批量评分，不是候选整体生成时间，也不是其他电脑的保证值。原始记录：`build/candidate-efficiency-20261110/model-final.jsonl`。

### 取消等待

使用受控阻塞的测试模型，确认模型已开始执行后设置请求取消事件；更新响应不再标记 pending，不发布旧候选，重复查询也不会重放。一次记录的更新往返为约 0.30 ms；合同断言针对取消行为，不用易受调度影响的毫秒阈值放宽/判定通过。

原逻辑在该场景仍可能等待完整的 60 ms 预算。新逻辑不保证所有设备都在 2 ms 内完成往返：2 ms 是等待片段上限，系统调度、IPC 和其他工作仍有开销。

## 复测与构建注意

```powershell
cmake --build --preset windows-release --target owo_candidate_pipeline_benchmark owo_libime_batch_benchmark
cmake --build build/dependencies/libime-1.1.15/bridge-x86_64 --target owo_libime_bridge
```

桥接是独立工具链工程，不能只编译 Core 就认为模型 DLL 已更新；需要已配置的 MSYS2/clang64 依赖，并将其目录加入本次构建进程 PATH。停止占用 DLL 的开发 ModelHost 后，用 `scripts/stage_libime_runtime.ps1` 更新运行目录，再正常启动服务，不删除运行目录或停用安全软件。

Core 探针参数：`词典文件 输出JSONL [每组次数]`。不同版本分别构建并保留独立 EXE，再使用相同词典运行。模型探针参数：`旧桥接DLL 新桥接DLL 模型文件 输出JSONL`；各 DLL 目录必须包含匹配依赖。新增探针不会进入正常发行清单。

下一轮优先定位复杂纠错/候选召回本身、导入词库重建和未取消的跨宿主排队，而不是继续只优化热缓存。可通过安装版“调试与性能”采集真实设备上的对应阶段；本轮的 `model_prepare_us` 是候选元数据准备子阶段，包含于 Core 布局/准备时间，不应重复相加。

回滚本次提交并重新构建即可恢复原逻辑，无配置、词库或模型格式迁移。
