# OwO 候选生成链路梳理报告

日期：2026-11-10（Asia/Shanghai）

源码基线：`0474e3a`；项目版本：0.2.9。

方法：源码调用链审阅、构建配置和既有测试/文档清单核对。

本次不修改候选算法，不执行全量自检、质量批测、性能基准或付费 API 请求；不改动日常词频、插件、配置、注册及运行进程。本文的“已确认”指代码行为已确认，不代表已在全部应用或另一设备复现。历史测试和旧基准不能充当本次验证结果。

审阅期间另有 `src/tsf/selection_assistant.cpp` 的未提交提示文案改动；该改动不属于本报告，予以保留。本文的选区辅助功能边界按上述提交基线说明。

## 1. 结论摘要

1. 普通拼音的正式链路是：TSF 编辑状态 → 后台请求 → Core 解析/词典/组合 → 评分和分区 → 候选缓存 → 可选 ModelHost 重排 → TSF 校验/渲染 → 上屏与学习。
2. 不是“一次解析、按总分排序、直接绘制”。首轮快速候选、后续纠错/扩容、模型更新是不同阶段；完整度保护、词频偏好、分区配额、缓存稳定性都可能改变原始分数顺序。
3. 基础词典已使用 v2 只读内存映射、整数音节和预建索引；不能继续将“每次展开 188 万条 std::string”当作当前默认实现。但导入词库仍有文本加载、注音恢复和内存索引重建成本。
4. 普通第一页已移除原先最低 32 项搜索限制，但生成器仍有最低 12 项质量余量，Core 分区又会放大预算。例如默认页长 7：快速轮次上限取 18，完整轮次预算通常取 48，不能理解为内部仅搜索 7 项。
5. ModelHost 不阻塞普通基础候选的首次生成路径，但模型更新等待仍占用串行 Core；符号兼容的后续行还可能同步等待自己的模型结果。因此“基础候选完全不受模型延迟影响”说法过强。
6. 当前智能排序是本地 libime n-gram 评分加宿主规则，不是大模型全文理解；“模型管理器 API”是独立的选区改写功能，不参与普通候选排序。
7. 候选分区存在两层处理：生成器先保留各源配额，Core 再编排可见页，并在模型结果发布时保留必要结构。排查“目标词被挤到后页”不能只看 `Candidate.score`。
8. 已有请求淘汰、取消事件、断线取消、LRU、增量解析、堆式 Beam、批量模型入口和原子绘制等优化；主要剩余风险是串行阻塞、前置剪枝、规则分散、导入词库重建和诊断粒度不足。
9. `CandidateScheduler`、Provider continuation 等接口已存在，但没有接入 `run_core_server` 的普通拼音候选分支；不能将其描述为已替代正式搜索的实时多源调度器。

## 2. 总体流程与职责

```text
焦点应用中的键盘 / 鼠标
  └─ OwO.TSF.dll（应用进程内）
       ├─ 快捷键、中英模式、光标、符号、已选暂存片段
       ├─ 插件输入方案 ── 独立 InputMethod IPC / SessionRouter
       ├─ 选区 + v ───── 独立模型辅助进程 / HTTPS API
       └─ 内置拼音 / exact_code
            └─ 单候选工作线程 + 可替换 pending_request
                 └─ 持久 Core 命名管道
                      └─ Core 串行请求处理
                           ├─ 配置 / 词库快照
                           ├─ 符号兼容适配
                           ├─ 解析与纠错
                           ├─ 词典、学习词、缩写、前缀、组合候选
                           ├─ 评分 / 限额 / 分区 / 稳定候选池
                           ├─ 基础 candidate_response ───────────┐
                           └─ 可选单工作队列 → ModelHost         │
                                └─ libime 批量评分、受约束重排     │
                                     └─ candidate_update_response │
                                                                 ↓
                   TSF 校验请求身份 → 应用快照 → 布局 / 绘制 → 选择
                                                                 ↓
                          TSF EditSession 上屏 / 暂存 / 消耗输入前缀
                                                                 ↓
                                    candidate_committed → Core 学习
```

| 层 | 主要职责 | 不应混同的职责 |
| --- | --- | --- |
| TSF | 输入状态、焦点、光标、候选交互、编辑会话、渲染 | 不直接运行 libime，不在按键回调中进行词典组合搜索 |
| Core IPC | 配置/词库选择、解析和候选搜索编排、缓存、分页、反馈 | 当前也承担不少具体排序规则，并非纯传输层 |
| Engine | 拼音解析、词典查询、组合、基础评分、部分分区规则 | 不直接执行 Windows 文本上屏 |
| ModelHost / bridge | 对给定中文候选做本地语言模型评分 | 不从任意拼音无限制生成新文字，也不替代宿主安全和分区约束 |
| 设置中心 | 写配置、词库快照、插件状态和用户模型设置 | UI 显示成功不等于正在输入的进程已加载同一 TSF/配置 |

## 3. 数据模型与必须保持的约束

| 字段 / 状态 | 含义与单位 | 关键约束 |
| --- | --- | --- |
| `input_buffer_`、光标 | TSF 的 UTF-16 输入；普通拼音主要为 ASCII | 符号兼容引入非 ASCII 后，不能直接当 UTF-8 字节数 |
| `normalized_input` | Core 归一化编码 | 普通拼音转小写，保留手动边界；展示仍保留原输入大小写 |
| `Syllable.begin/end` | 原归一化输入中的半开字节范围 | 不是输出汉字位置，也不是补全后的读音长度 |
| `syllables` | 候选使用的规范音节 / 编码 | 可与实际键入片段不同，如简拼、补全和纠错 |
| `source_segments` | 对应的原始输入片段 | 拼音预览不能直接用候选的完整读音替换用户输入 |
| `consumed_input_bytes` | 当前候选消耗的输入前缀长度 | 上屏后只删除该范围；符号适配后必须转换成 TSF 所需单位 |
| `segment_count`、`segment_lengths` | 组成候选的词条片段数量及长度 | 不是拼音音节数量；字典整词和组合句据此区分 |
| `score`、`coherence_score` | 基础分及跨边界证据 | 不是最终显示序号；不能单独解释页面位置 |
| `user_lexicon`、`provisional_user_word` | 用户词身份及临时状态 | `user_preferred()` 比单纯加分更强，但全输入与部分输入仍区分 |
| `qualified_sentence_reading` | 经质量筛选的整句读音方案 | 用来计算句子总配额和分割多样性，不是“所有可解析路径” |
| `model_only` | 供模型比较的隐藏项 | 隐藏项要连续在尾部；不能截断可见页或当作额外协议额度 |
| `candidate_groups` | 句子 0、词语 1、单字 2 | 必须与正文、消耗范围同时移动；分区槽位不等于纯分数层级 |
| 请求 ID + generation | 请求与组合态身份 | 再加页号、展开状态和纠错状态校验，拒绝过期回复 |

协议当前版本 15，单帧上限 1 MiB，候选列表最多 256 项。JSON 解码拒绝非法/未知字段；不是对外永久稳定协议。请求 ID 在 TSF 构造时混入 PID 和时钟，再递增，避免只从各进程的 1 开始。

证据：[候选结构](../../include/owo/engine/candidate_generator.h)、[解析结构](../../include/owo/engine/input_schema.h)、[消息](../../include/owo/protocol/messages.h)、[信封](../../include/owo/protocol/envelope.h)、[请求身份初始化](../../src/tsf/text_service.cpp#L915)。

## 4. TSF：按键、排队和回包

### 4.1 按键路由

`OnTestKeyDown` / `OnKeyDown` 先处理选区模型辅助功能，再处理插件输入方案及普通输入逻辑。普通链路还包括中英切换、快捷键、方向键、小键盘、标点、手动拼音分隔符与删除。

`queue_candidate_request()` 对插件方案转入 `queue_plugin_compose()`；内置方案进入 `schedule_candidate_request()`。原 Agent 模式会从待解析串中去掉开头的 `v`。符号兼容只在中文、全拼且非 Agent 模式下启用。

### 4.2 最新请求优先

- TSF 维护一个可替换的 `pending_request_`，新输入覆盖未发送请求；反馈使用另外的队列。
- 新请求触发旧取消事件，更新原子 `latest_candidate_request_id_`。
- 工作线程优先取候选请求，否则才处理反馈；不会每个按键新建 `std::async`。
- 持久管道复用快速输入/翻页；空闲约 50 ms 后释放，给其他应用连接串行 Core 的机会。
- 首屏默认请求快速候选；需要精化时，约 4 ms 防抖后在没有更新输入的条件下发送同身份的完整轮次。
- 请求超时随输入长度在 900–2500 ms 内调整。这个数是容错截止，不是正常响应性能目标；首次失败还有一次自动重试。

证据：[排队与取消](../../src/tsf/text_service.cpp#L4012)、[工作线程](../../src/tsf/text_service.cpp#L4143)、[持久客户端](../../include/owo/ipc/named_pipe.h)。

### 4.3 回包安全与旧帧保留

收到响应先校验协议、请求 ID、类型及纠错模式；回到 UI 线程后再校验 generation、请求 ID、页号、展开状态和输入是否仍存在。正文、消耗范围和分组不一致时不会作为有效候选提交。

新输入尚未得到匹配快照时，保留旧画面和几何，避免状态条/空帧来回切换；待处理标志和延迟确认机制阻止把旧画面误上屏。空的“仍需精化”响应与最终空结果被区别处理。模型更新用 `preserve_paging`，不重写拼音预览和普通翻页状态。

这只证明已有防闪烁机制，不证明桌面上绝无闪烁；亚克力背景采样、窗口大小、宿主失焦和渲染失败仍是独立因素。

证据：[回包应用](../../src/tsf/text_service.cpp#L4537)、[快照一致性说明](../candidate-snapshot-consistency.md)。

## 5. Core：配置、词库和缓存

### 5.1 实际词典装配

Core 启动加载基础词典及用户词频，启动配置监控。生产候选生成器的 `BigramModel*` 参数传入的是 `nullptr`；真实 libime 在后续 ModelHost，不是在 Beam 的每次转移中直接调用。

按词库管理器的快照，Core 在基础词典、导入词典、两者合并或空词典之间选择。用户词/别名经 `ManagedDictionaryModel` 接入；中文音节词条进入 phonetic 索引，无法作为普通中文读音词处理的映射保留为显式编码别名。

关闭基础词典后，只要启用的第三方词库有有效注音，仍可查询、简拼/混拼、组合；但不是把所有无注音文本都自动变成可用拼音词，也不能保证小词库独立运行时有足够单字、常用词和跨边界证据。

### 5.2 已完成的底层优化

- v2 基础词典：`CreateFileMappingW` / `MapViewOfFile` 只读映射、整数音节 ID、紧凑词条/文本区、预建首字母和混拼索引。
- 安装阶段写 `.validation` 记录；运行时匹配记录后避免再完整扫描 payload 校验和。仍保留文件布局/边界检查，不是完全不校验。
- 查询提供 `string_view` 结果；生成器还有单请求精确查询、最大词频和搭配证据缓存。

证据：[基础词典加载](../../src/engine/binary_lexicon.cpp#L373)、[首字母查询](../../src/engine/binary_lexicon.cpp#L968)、[混拼查询](../../src/engine/binary_lexicon.cpp#L1093)。

### 5.3 导入词库仍有的成本

`ManagedDictionaryModel::refresh()` 约每 250 ms 检查快照指针；变化后在当前 Core 请求执行路径读取 `active.tsv`、校验词条、恢复注音并建立 `IndexedLexicon`。该路径上限包含 256 MiB 快照和 50 万行，不等同于低延迟保证。

因此词库更新、首次启用大型词库后的候选请求可能承担重建成本；基础词典 mmap 并未自动解决这部分。

证据：[导入词库刷新](../../src/engine/managed_dictionary.cpp#L25)、[Core 装配](../../src/ipc/named_pipe.cpp#L1355)。

### 5.4 候选 LRU

容量 128，键包含输入、前一编码、中文上下文、配置 generation、学习 generation、临时学习 epoch、解析预算、纠错和上下文排序开关，以及必要的符号布局。

页号和展开状态不直接成为不同候选身份：缓存存整段输入的候选池，再取页。请求更深时可扩容，但保留已展示前缀；模型成功后也发布回同一缓存。缓存返回当前实现会复制 `ParseResult` 与候选向量，不是全程零拷贝。

稳定性与即时最优有取舍：保留旧前缀避免翻页/展开结果跳变，也意味着更宽搜索后来发现的更高分候选，不应任意打乱已展示位置。

证据：[缓存键与快照](../../src/ipc/named_pipe.cpp#L517)、[LRU](../../src/ipc/named_pipe.cpp#L631)、[扩容保序](../../src/ipc/named_pipe.cpp#L564)。

## 6. 拼音分割与纠错

1. 全拼解析只接受 ASCII 字母和作为分隔的 `'`，转小写；前导单引号和连续边界等非法形式被拒绝。标点等字符需先走符号组合适配。
2. 生成多条 `ParsePath`，区分 exact、不完整补全、corrected、简拼/混拼补全，并保留来源范围。
3. 手动边界优先，不允许无边界回退把 `quan'loi` 擅自改成逐字母方案；“关闭纠错”不等于关闭简拼、不完整拼音与合法多分割。
4. Core 先生成非纠错候选；候选不足或缺少严格整段证据时，才考虑纠错。纠错开关开启不代表每次都运行编辑距离搜索。
5. 快速轮次可以延后纠错，完整轮次再补。原始分割和修复读音可以并存，但受路径/候选预算限制。
6. 短输入解析可复用前一串的共同稳定前缀，同时检查是否出现跨边界新音节；不是任意复用第一个方案。
7. 长度至少 12 且没有显式分隔的紧凑拼音，Core 特意绕开普通增量复用以保证同一完整输入的确定性，严格轮次最多取 16 条路径；常规主路径预算 32。
8. 纠错实现的输入范围为 3–128 字节；短串最多 1 次编辑，至少 12 字节时最多 2 次编辑，并受 Beam 等条件约束。普通输入限长 256 不意味着 256 字节都享有相同纠错能力。

拼音预览选择“来源分割”，不直接补成候选的完整读音。短串通常尊重首选完整 exact 分割；有可靠整段字典证据的候选可以影响边界选择。协议无法容纳的超长片段会留空分割信息，让 TSF 保留原始输入，不通过伪造切分凑上限。

证据：[解析实现](../../src/engine/full_pinyin_schema.cpp#L1026)、[增量解析](../../src/engine/full_pinyin_schema.cpp#L861)、[纠错边界](../../src/engine/full_pinyin_schema.cpp#L553)、[Core 严格/纠错编排](../../src/ipc/named_pipe.cpp#L1939)、[预览选择](../../src/ipc/named_pipe.cpp#L344)。

## 7. 候选召回与组合

正式入口为 `CandidateGenerator::generate()`，不同输入可走不同快捷分支；不能把以下过程视为每次都完整执行。

| 来源 | 作用 | 主要约束 |
| --- | --- | --- |
| 显式编码映射 | 支持导入别名等完整编码映射 | 不等同于中文拼音分解得到的词条 |
| 学习词精确/关联召回 | 同一学习词可从完整、简拼、混拼读法召回 | 验证音节与原输入对应；不是只按文本开头随意补长句 |
| 整段字典词 | 按整条读音直接查词 | 区分完整匹配、补全、纠错和来源分割 |
| 混拼/声母索引 | 为 `wsm`、`bugd` 等找词 | 有界查询、读音匹配、单字和词语分类 |
| 首字/前缀字典词 | 为分段选择提供“你好”“这款”等 | 只消耗原输入前缀，需要携带准确消耗范围 |
| 组合搜索 | 由已安装词典词条覆盖整条读音 | 有界 chart/Beam；先比较胜出可能再复制文字/状态 |
| 边界连贯性证据 | 检查候选在另一种分词边界上的真实词典覆盖 | 常见局部跨度上限 4 字，不是完整句法分析 |
| 隐藏模型备选 | 让模型比较基础展示中未保留的有限同音/结构备选 | 有质量门控及数量上限，不直接展示 |

生成器内部按候选正文做去重，重复时优先较完整消耗范围、有效学习偏好、整词身份等，再比较分数。结果不是为同一正文保留全部消耗范围/读音的多重记录。协议和缓存的稳定匹配又使用正文加消耗范围，维护时必须注意两层身份定义不同。

组合 Beam 并不穷尽所有同音字排列；这既控制噪声与耗时，也意味着被早期剪枝的优质候选，后续 libime 不能凭空恢复。扩大输出项数也不等于重做无上限召回。

证据：[正式生成器](../../src/engine/candidate_generator.cpp#L821)、[正文去重](../../src/engine/candidate_generator.cpp#L389)、[Beam 主循环](../../src/engine/candidate_generator.cpp#L1543)。

## 8. 评分、重排与人工先验

基础搜索的概念式为：

```text
词条静态分之和
  - 额外词条片段惩罚
  - 不完整/纠错/简拼成本
  + 首选分割、局部匹配及用户学习证据
  + 跨边界词典连贯性和有限搭配证据
  + 最短完整分割的一次性小幅奖励
```

这不是能解释每个最终位置的唯一公式：某些规则是候选身份/排序层级/配额，不是加分。

| 规则 | 当前代码数值 / 行为 |
| --- | --- |
| 词条静态分 | `1000 × log1p(frequency)` |
| 额外组成片段 | 每多一个词条片段约减 22000 |
| 不完整路径 | 基础减 1500，补全字符再乘 750 |
| 纠错路径 | 每次编辑减 6000 |
| 简拼路径 | 基础成本 8000，并结合补全字符成本和专门匹配逻辑 |
| 首选完整分割 | 基础先验 16000，长句按已有尺度减弱 |
| 字典整词与等字数组合句 | 满足条件时，组合句小幅减 1500；明确学习词等豁免 |
| 最短完整分割 | 多种合格完整分割并存时，少音节方案加 1000；整串一次、幂等 |
| 连贯性 | 有界词典覆盖证据及未覆盖边界惩罚，不是 CCKB/LTP 全句推理 |
| 搭配缓存 | 最多 256 条请求内紧凑记录，字典证据命中为 1000；所用简拼转移路径累计受 2000 上限约束 |

明确存在人工语言先验：单声母 `d` 对“的、都、对、等、到、但”有专门种子优先级；`n → ni`、`m → ma` 也有偏好。因此不能把当前实现描述成“完全无文字/拼音特判”。这些先验是否继续保留、数据化或扩大覆盖，需要产品和质量数据共同决定。

`CompactCollocations` 当前是请求内、由已安装字典验证的词对证据缓存；未发现正式候选链路加载外部 CCKB 搭配数据库或 LTP 句法模型的入口。类名含 collocation 不等于已接入独立搭配语料库。

证据：[分值定义](../../include/owo/engine/candidate_scoring.h)、[计算](../../src/engine/candidate_scoring.cpp)、[人工声母先验](../../src/engine/candidate_generator.cpp#L188)、[紧凑搭配](../../include/owo/engine/compact_collocations.h)、[搭配调用](../../src/engine/candidate_generator.cpp#L1570)。

## 9. 分区、分页与展开

### 9.1 分区不是最后一次按分数排序

先在生成器保留各源容量，再由 Core 的 `arrange_partitioned_candidate_pages()` 构造页；部分候选还进入等字数词语/句子联合评分带。模型应用后仍受完整度、置信度、分组及学习保护约束。

主要规则：

- 分区开关开启且页长至少 4 才走普通分区布局；1–3 项页长仍合法，但不启用这套分区。
- 合格整句读音方案的总句子上限为 `max(1, 方案数) × 2`，是上限而非必须补足数量；每种来源分割也有最多两个的约束。
- 每页最多两个句子，且为仍有候选的词语区/单字区留位置；不同分割方案按既定跨页多样性规则安排，不是句子仅第一页可见。
- 扣除句子后的剩余名额：词语区向下取整、单字区向上取整；来源不足可以补位。没有句子且页长 5 时，通常是 2 个词语、3 个单字。
- 输入本身可完整组成一个音节且配置允许时，每一页把单字区置于词语区之前；不是只改变首页。
- 在适用的分区字典区，组合词只补两页容量的缺口：`max(0, 2P - 实际字典词数)`；这与下一条不完整输入总配额是不同约束。
- 被判为不完整输入时，所有非单字候选共享 `2P` 上限，包括字典词、学习词、部分前缀、组合句和隐藏模型项；不是仅限制随机组合。
- 完整 exact 候选已存在时，不完整输入限额的判定有豁免条件；不能仅凭输入短就断言一定启用 `2P` 限额。

### 9.2 分页身份

Core 和 TSF 共享 `candidate_page_boundaries()`。由于每页句子上限，一页允许少于配置页长；不能始终用 `page × page_size` 推导真实边界。

展开请求必须从页 0 开始，返回最多 256 项的可见池，不等于穷尽整本词典。TSF 将其作为多行候选页，区分“当前选中页”和“滚动窗口第一行”，数字键跟随选中页；默认最多约 5 行可视。

候选池不足时，翻页/展开可能触发扩容；缓存已有候选前缀受到保护。模型成功发布也会更新该池，减少“基础页和展开列表两套答案”。这仍需要同一输入、上下文、配置及学习代数；变更这些条件后不是同一快照。

关闭分区不意味着回退成毫无特殊规则的全局排序：兼容双声母布局、完整度/学习保护、生成器质量规则等仍存在。

证据：[Core 分页](../../src/ipc/named_pipe.cpp#L968)、[候选分区规则](../../src/engine/candidate_partition.cpp)、[共享页边界](../../include/owo/protocol/candidate_pages.h)、[TSF 展开模型](../../include/owo/tsf/expanded_candidate_pages.h)、[展开入口](../../src/tsf/text_service.cpp#L5237)。

## 10. 智能排序与上下文的真实范围

### 10.1 上下文从哪里来

普通候选的 `recent_language_context_` 主要由 OwO 成功上屏的内容累计，默认保留最后 24 个 UTF-16 单元；请求时叠加已选但未上屏的暂存词。前一段编码另外通过 `input` 字段传递。

失焦、文档切换、部分文本导航等路径会清理普通排序上下文。因此，刚点击到任意已有段落后输入，不保证能识别那段文档的前文；经其他输入法输入、粘贴、程序改写的内容，也不应直接假定已被纳入普通排序上下文。

不要把 Agent 的较大本地上下文历史、应用标识、选区模型的附近文本，与普通 libime 排序的 24 单元窗口混在一起。

### 10.2 三种“上下文能力”

1. 基础候选的词典边界覆盖/连贯性：由字典结构提供，不等于文档语义。
2. 用户学习及有界跨词连接证据：包含输入→词、前文后缀→输入→词；部分语境相关策略由智能排序开关控制。
3. libime：对候选中文和传入的中文前文分词评分，返回候选的排列；只在允许的结构与置信层级内拥有排序决定权。

生产生成器未配置 `MemoryBigramModel` 不等于完全没有上下文：libime 在独立后处理里，用户学习也是另一条路径。

证据：[24 单元窗口](../../include/owo/tsf/language_context.h)、[请求上下文](../../src/tsf/text_service.cpp#L4052)、[失焦清理](../../src/tsf/text_service.cpp#L1078)、[Core 上下文提升](../../src/ipc/named_pipe.cpp#L873)。

### 10.3 模型调用与约束

- 默认配置不开智能排序；启用后，普通首页在适用条件下提交本地 ModelHost。
- Core 采用单模型工作队列，待执行任务只留最新；已经进入 IPC/桥接调用的任务不能靠清空队列立刻中断。
- libime 按中文词条做有界分词，桥接最大词长 4 字、分词 Beam 宽度 8；不是把整句一律当未知词评分。
- 支持批量桥接入口，旧 bridge 仍可退回单项接口。但当前 batch 内部逐候选调用 `score_candidate()`，每次也重新处理同一 context；“批量调用”尚不等于共享计算 DAG 或只编码一次前文。
- 隐藏备选和少量跨页合格句子可被模型召回；模型不能生成池外任意文字。宿主先保护整段覆盖，再比较置信度、模型名次等，保留必要的学习偏好和分区规则。
- TSF 在基础响应后只执行一次更新循环；Core 对未完成模型有界等待 `min(model_timeout,60 ms)`。若仍返回 pending，当前 TSF 不会无限轮询，因此“服务端最终计算完成”不必然意味着这一轮 UI 应用。
- 默认模型超时 50 ms，设置合法范围 5–500 ms；批量 C ABI 内部没有贯穿分词循环的停止令牌，不能把设置值解释为硬性 CPU 执行中断。

证据：[模型队列](../../src/ipc/named_pipe.cpp#L458)、[提交](../../src/ipc/named_pipe.cpp#L2810)、[更新等待](../../src/ipc/named_pipe.cpp#L1782)、[TSF 更新](../../src/tsf/text_service.cpp#L4470)、[libime 后端](../../src/model/libime_backend.cpp)、[桥接分词与 batch](../../tools/libime_bridge/libime_bridge.cpp#L46)、[模型排序保护](../../include/owo/ipc/contextual_candidate_order.h)。

## 11. 符号兼容的附加链路

符号适配不在普通拼音 parser 内硬塞非字母，而是保留原组合串、拆分语义段、生成当前段，再把符号投影回候选和预览。

- 强分隔、弱引号与字面符号分别处理；单引号是否是手动边界受快捷键配置及手动标记控制。
- 当前首段负责数字、翻页和展开；后段普通预览行使用同一个 Core evaluator 生成，而非另一套精简排序。
- 某些强分隔可按候选最大字数合并为一个候选项；不是简单把后一行接到候选栏尾部。
- 后段预览最多保留 16 行，并有约 25 ms 的切片门限；该门限在行之间检查，单行较慢时仍可超出。
- 后段可以同步提交自己的模型任务，完成后再继续响应；这是普通“基础先显示”链路的一个例外。
- 展开状态不显示后段预览行；首段消耗后下一段成为活动段。

此路径最需要检查 UTF-8 字节 / UTF-16 光标单位、符号位置、手动边界和真实候选页内容的一致性。

证据：[符号适配](../../src/engine/symbol_composition.cpp)、[同 evaluator 后续行](../../src/ipc/named_pipe.cpp#L2975)、[TSF 消耗单位转换](../../src/tsf/text_service.cpp#L4388)。

## 12. 上屏、剩余拼音与用户学习

### 12.1 正常提交

数字/鼠标选择最终进入 `commit_candidate()`。它验证候选和消耗长度，构造 TSF 编辑会话；只有成功上屏后才更新上下文、删除被消耗的前缀并反馈学习。部分词被选择后，剩余串重置页面、提升 generation、再次请求候选。

关闭“候选词直接上屏”时，已选内容进入带原拼音的暂存结构；后续请求把暂存文字计入上下文，最终提交时再处理各片段和可靠的组合学习链。学习链验证文档和插入锚点，不应通过任意周边文本猜测新词。

“最终上屏但并非一次候选选择”的组合学习，不等于监控整个应用的全部文本变化；通过其他输入法或应用自身生成的所有内容，不保证都能学到。

### 12.2 Core 学习

Core 对输入与文字做读音/字数对齐验证。对齐后才建立编码→词和语境记录；未对齐的完成词等仍可记录全局使用次数，但不能把短输入误记为完整拼音编码。

学习分为：全局词频、编码内词频、前文后缀+编码词频、可召回的用户词。相关读法召回让完整拼音、简拼、混拼共享学习证据，但不是无限制补全后续未输入音节。

### 12.3 当前衰减与持久化

- 灵敏度 1–10，越高分值增益越大，默认 10；三层增益不同，采用有界饱和曲线。
- 单次观察的强偏好约 10 秒；单次分值到 30 秒约余 25%，到 60 秒为 0。已有多次证据不等于也按 60 秒清空。
- 全局、编码、语境计数上限分别为 256、128、64；触顶时相关竞争组按 3/4 衰减，再加入新证据。
- 临时学习存在时，候选缓存通过约 5 秒 epoch 避免永远保留过期加分。
- 反馈累计 32 条刷盘，正常 shutdown 会刷新剩余记录；不能保证强杀、断电前未落盘的尾部证据保留。
- 关闭“用户学习”会阻止新增反馈记录，但旧学习数据是否参与候选还取决于用户词库来源开关；`ManagedDictionaryModel` 读取旧学习的条件不直接使用该配置开关。这是需要明确说明的产品语义，不宜把“停止学习”自动理解为“移除已有个性化”。

证据：[提交与余串](../../src/tsf/text_service.cpp#L5613)、[学习反馈](../../src/tsf/text_service.cpp#L4126)、[Core 对齐](../../src/ipc/named_pipe.cpp#L2925)、[衰减](../../src/engine/user_frequency.cpp#L333)、[计数/灵敏度](../../src/engine/user_frequency.cpp#L405)、[持久化](../../src/engine/user_frequency.cpp#L624)、[学习读取门控](../../src/engine/managed_dictionary.cpp#L139)。

## 13. UI 渲染与焦点

候选文本在 TSF 进程内用 Direct2D / DirectWrite 绘制到离屏表面，再由 `UpdateLayeredWindow` 连同几何发布；不是 WinUI 设置中心窗口直接渲染候选。

同模式输入更新时保留原窗口尺寸，待对应候选到达后再更新布局；先发布主表面，再处理阴影。存在主题背景采样、阴影、DPI/工作区裁切、置顶和 owner 绑定逻辑；TSF UI-less 宿主还可能接管候选展示。

因此排查闪烁应先分三类：

1. 状态空帧：旧候选提前清空、精化 pending 被当最终空结果。
2. 几何变化：拼音/候选两次调整尺寸、分页元数据错位。
3. 材质/窗口层：背景截图含自身、阴影旧表面、设备重建、Z-order/焦点变化。

现有 `render_us` 只包围对应结果处理中的 `update_candidate_window()`，不是从按键到屏幕合成完成的端到端延迟；即时按键重绘和系统 compositor 耗时不能由该字段独自代表。

证据：[绘制入口](../../src/tsf/text_service.cpp#L2551)、[原子表面发布](../../src/tsf/text_service.cpp#L2344)、[结果应用日志](../../src/tsf/text_service.cpp#L4659)、[窗口顺序策略](../../include/owo/tsf/candidate_window_order.h)。

## 14. 其他输入方案及大模型功能的隔离边界

| 功能 | 实际路径 | 与普通候选的关系 |
| --- | --- | --- |
| `exact_code` | ExactCodeSchema + 通用生成器 | 不启用全拼特有音韵辅助 |
| 插件输入方案 | TSF → InputMethod IPC → SessionRouter/Worker → 已授权插件 | 有独立会话/候选 ID/消费范围/提交确认；复用部分候选 UI |
| Agent IPC 插件 | `v` 开头组合、拼音选择暂存、Agent 结构化会话 | 原 Agent 模式不是模型管理器选区翻译；不负责普通拼音 LM 评分 |
| 选区模型 API | 安全选区 → 功能菜单 → 独立辅助进程 → HTTPS → 校验选区后替换 | 默认关闭；不经过 CandidateGenerator 和 libime 排序 |
| 亚克力 / Unicode | 候选主题资源 / 符号数据 | 资源插件不应改变词典召回或算法分值，视觉问题须与质量问题分开 |

边界审阅还看到两项与近期安装问题相关、但不属于普通候选算法的遗留行为：

- `is_agent_mode()` 主要依据输入开头 `v` 或会话状态判断，没有在这一判断中绑定插件启用状态；因此“还看到 v 模式”不等于插件仍获准执行。PluginHost 在调用前另校验活动绑定和权限。
- 选区辅助进程定位用 TSF 模块的两级父目录。对安装布局 `bin/x86/OwO.TSF.dll` 会推导到错误的 `bin/settings`；属于 32 位宿主兼容问题。本报告仅记录，不在审阅中修复。

## 15. 当前预算与边界速查

| 项目 | 当前值 / 条件 | 不能误读为 |
| --- | --- | --- |
| 内置拼音输入长度 | TSF 最多 256 个输入单元；常规拼音为 ASCII | 任意超长错拼都能纠正 |
| 完整纠错输入范围 | 3–128 字节，并有条件门控 | 256 字节均有完整纠错 |
| 主解析路径预算 | 通常 32；长紧凑串严格轮次 16 | 所有可能分割都会参与组合 |
| 生成器最低搜索余量 | 12 | 最多只生成 12 条 |
| 默认 P=7 首屏快速预算 | `min(full, max(P+1,2P+4))`，典型为 18 | 只搜索屏幕上的 7 条 |
| 默认 P=7 分区完整预算 | 典型为 `(P+1)×4+16 = 48` | Beam 也只有 48 个转移 |
| exact Beam | 通常 `max(16或32,search_limit×4)` | 输出项数等于搜索状态数 |
| 隐藏模型备选 | 生成器额外池最多 64，最终模型协议总数仍最多 256 | 隐藏项不占任何资源/额度 |
| 候选结果 LRU | 128 个键 | 128 条候选总量 |
| 单次展开 | 最多 256 个可见项 | 词典全量枚举 |
| 普通页号 | 0–100 | 每个输入一定有 101 页 |
| 内置候选页长 | 合法 1–9；默认 7 | 所有页都必须填满 |
| 单字区交换 | 配置开启且输入符合完整单音节等条件 | 任意短输入均交换 |
| 非单字不完整配额 | 适用时总量不超过 2P | 每页都有 2P 项，或只限制随机句子 |
| ModelHost 超时 | 默认 50 ms，配置 5–500 ms | 原生分词可被硬中断于指定毫秒 |
| 普通上下文 | 默认最后 24 UTF-16 单元，加暂存内容 | 全文、跨应用无限记忆 |
| 配置刷新 | Core 监控默认约 250 ms；TSF 按需约 500 ms；主题另有约 1 s 检查 | 所有前后端同一瞬间切换 |

以上是静态预算和条件推导，不是本次测得的毫秒性能结果。Beam 中还会查询多个词条、展开多条路径，因此预算不能直接换算成固定 CPU 时间。

## 16. 已确认风险与建议优先级

这里的优先级用于后续工程安排，不把所有设计取舍都当作已复现故障。

| 编号 | 优先级 | 代码事实 / 风险 | 建议 |
| --- | --- | --- | --- |
| R1 | P0 | Core 主候选管道单连接串行；慢输入、较长持久连接、模型更新等待会影响后续请求 | 明确会话公平性、候选/控制任务边界；设计有界调度，先保一致性再并发化 |
| R2 | P0 | 日志主要为阶段汇总，缺少单候选“在哪一步被拒绝/降级/截断”的解释 | 增加开发模式可选 CandidateTrace，先解决质量问题不可解释性 |
| R3 | P1 | 解析路径、exact 路径数、Beam 和候选池均会剪枝；LM 只能重排留存/隐藏项 | 记录目标消失阶段，按召回不足/评分错误/布局隐藏分别修，不能一律加权 |
| R4 | P1 | ModelHost 更新等待占串行 Core；TSF 更新循环有次数边界，过晚结果可能不应用 | 非阻塞结果发布或有界后台重试；绑定当前组合快照，翻页/输入变化立即淘汰 |
| R5 | P1 | batch 桥接仍逐候选重新处理 context，原生调用内无细粒度取消 | 复用前文 LM 状态、词边界与共享前缀；加入可观测的 deadline/取消检查 |
| R6 | P1 | 大型导入词库快照在请求线程同步加载与建索引 | 后台构建不可变索引后原子交换；进一步考虑离线编译/映射导入词库 |
| R7 | P1 | 反馈与候选共用 TSF 工作者，候选优先；累计刷盘遇强杀可能丢尾部 | 有界反馈队列、可合并反馈、周期/空闲刷盘及正常停机协议，不阻塞按键 |
| R8 | P1 | 词语、句子、完整度、联合评分带规则分散在 Engine/Core/模型发布阶段 | 建立明确阶段契约和单一快照结构；拆模块但不在无回归数据时整体重写 |
| R9 | P1 | 代码有 `d` 六字种子、n/m 拼音偏好等人工先验 | 数据化并标注来源、开关/版本；与“禁止样例硬编码”的目标明确对齐 |
| R10 | P1 | Core 默认配置路径、设置中心环境覆盖、TSF 读取策略不完全相同 | 统一运行时配置/词库/插件身份诊断；先证实实际路径，不凭 UI 开关判断后端 |
| R11 | P2 | 全量路径由单个大型文件承担，Candidate 还有跨层平行数组和隐式尾部约定 | 封装候选快照及强类型单位，降低新增方案/标点/模型功能的改动面 |
| R12 | P2 | 学习开关、用户词库开关、预测补全开关含义不同；旧文档还出现“全局最多两句”等过时表述 | 统一产品说明与合同测试，文档标明代码基线和历史边界 |

可量化的耦合位置：审阅时 `text_service.cpp` 6593 行、`named_pipe.cpp` 3200 行、`candidate_generator.cpp` 2899 行、`full_pinyin_schema.cpp` 1306 行。行数不是缺陷证明，但结合其中交叉职责，可解释为何局部调整容易产生跨阶段回归。

## 17. 建议的诊断与验证体系

### 17.1 按故障表现分流

| 表现 | 首先排查 | 不宜直接采取的操作 |
| --- | --- | --- |
| 完全没有目标候选 | 解析路径、读音索引、来源开关、Beam/配额淘汰 | 未找到候选就盲目加分 |
| 目标在后页 | 原始分、完整度、学习身份、分区槽位、稳定前缀、模型保护层级 | 只比较两个 score 就断言最终排序错误 |
| 输入多一个尾字就变差 | 新分割/纠错分支、路径预算、增量复用与缓存身份 | 为单个例子新增固定文字替换 |
| 翻页和展开不同 | 同一快照键、可见/隐藏尾部、分组和共享页边界、模型缓存回写 | 用不同配置/上下文的结果直接比较 |
| 突然超时 | Core 排队、词库刷新、取消延迟、模型更新阻塞、IPC | 单纯继续扩大搜索或超时 |
| 看起来闪烁 | pending 空帧、几何重算、材质采样、焦点/Z-order | 默认认定是候选算法慢 |
| 学习一次很快失效 | 10 秒强偏好、60 秒单次分值、用户词库来源状态 | 把设计衰减当作磁盘记录丢失 |
| 重启后学习少了 | 反馈是否成功、32 条刷盘、正常停机/强杀、数据文件身份 | 直接清空用户词库 |

### 17.2 应补齐的可选开发轨迹

建议每个候选携带/记录：来源、完整度、实际消耗、原始分割、静态分、学习分、连贯分、一次性奖励、模型名次、质量门控原因、分区配额去向、裁剪阶段、最终页/槽位和快照 ID。

调试输出默认不收集真实输入/应用文本；需要文字证据时显式使用合成样例或用户授权数据。阶段耗时应区分：排队、首个可选候选、精化完成、模型应用、可交互、绘制提交和取消响应，不将缓存热查询当作冷输入性能。

### 17.3 已存在的验证入口

- 解析/生成/词频/词典：`tests/engine`。
- IPC 合同：`owo.ipc.local_correction_contract`、`candidate_snapshot_contract`、`joint_partition_contract`、`managed_dictionary_contract`、`core_config_contract`、`model_confidence_contract`、`singleton_decay_contract`、`user_learning_contract`。
- TSF：`expanded_candidate_service`、`composition_learning`、`learning_anchor`、`input_method_context`、`pinyin_cursor`、`scheme_commit_session`、`wubi_commit_service` 等。
- 批量 CLI：复用生产 `run_core_server()`，使用独立根和私有管道；可比较完整输入与逐键输入、基础与 libime、5/7/9 页长、分区开关、学习开关、纠错开关、分页/展开。

## 18. 后续实施顺序

1. 先建立“候选来源 → 裁剪 → 排名 → 分区 → 最终页”的可解释轨迹和固定回归矩阵。
2. 测清冷请求、热缓存、导入词库刷新、模型更新和多应用切换各自耗时，定位真实首要瓶颈。
3. 解开串行 Core 上的模型等待与重索引；保证取消、公平性和快照一致性，再改变并发模型。
4. 对 libime 做上下文状态与共享前缀复用；不要只把更多单项计算包进 batch 接口。
5. 在既有快照、分区、学习及部分提交合同覆盖下，逐步将 Core evaluator、CandidateGenerator 与 TSF 状态/渲染职责拆分。
6. 最后才评估将 Provider/Scheduler 真正接入生产搜索；需证明质量、资源预算和分页稳定性，不以接口存在代替接入完成。

本报告没有给出“当前准确率/首选率/延迟已达标”的结论：这些需要在固定词典、配置、模型、学习状态、设备和宿主下重新采样。
