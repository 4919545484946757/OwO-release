# ADR 0036：可选择、可扩展的输入方案边界

- 状态：已接受
- 日期：2026-09-21

## 问题

引擎早期已经有 `InputSchema` 接口，但 Core 直接构造 `FullPinyinSchema`，候选生成器默认对所有输入执行声母、韵母、简拼、混拼和纠错逻辑，配置与设置中心也没有方案选择。因此接口在类型层面存在，运行时仍与全拼绑定。

## 决策

1. 配置 Schema v13 增加 `input_scheme`。当前稳定值为 `full_pinyin`，实验验证值为 `exact_code`；旧配置默认迁移为 `full_pinyin`。
2. `ParseResult` 携带方案标识与能力标记。候选生成器依据 `phonetic_assistance` 能力决定是否执行单声母、多声母、简拼、混拼、拼音补全和拼音专属初始加权，不直接识别具体方案；精确查词、分页、候选分区、用户学习、上下文排序和上屏保持方案无关。后续双拼可以启用该能力，五笔等表码可以关闭，而无需再增加候选生成分支。
3. `ExactCodeSchema` 将 ASCII 字母规范化为小写，只按显式 `'` 分段，产生唯一精确路径，不纠错、不补全、不做缩写。它用于验证五笔、仓颉、自定义表码等后续方案所需的 Core 路径；当前发布词典仍是拼音词典，因此该实验方案只能查询词典中已有的显式编码读音，不宣称为完整表码产品。
4. Core 在每次请求边界读取配置并选择解析器。配置代数已属于候选缓存键，因此热切换方案不会复用另一方案的解析或候选；切入精确编码时清空全拼增量解析状态。
5. 协议 v9 的 `syllables` 字段为兼容既有 TSF 保留，新的方案中解释为“显示片段”。`candidate_consumed` 始终表示原始输入的字节消费范围，不绑定拼音。

## 耦合审计

| 区域 | 处理结果 |
| --- | --- |
| Core 解析器选择 | 已从固定全拼改为配置热选择 |
| 候选生成辅助规则 | 已按解析结果的能力标记隔离拼音专属逻辑，不依赖具体方案枚举 |
| 精确词典查询、Beam、分页、分区 | 保持方案无关并由非拼音测试覆盖 |
| 设置中心 | 已提供输入方案选择；非全拼方案下禁用全拼纠错设置 |
| TSF `pinyin_cursor` 内部命名 | 行为只编辑预编辑 ASCII 缓冲，暂保留源文件名以避免无收益 ABI/测试迁移；用户界面改称预编辑编码光标 |
| Agent v3 `raw_pinyin` 等字段 | 属于已发布第三方兼容字段，本次不破坏性重命名；后续 Agent v4 应并行增加 `scheme_id`、`raw_input`、`segmented_input`，至少保留一个版本的旧字段映射 |
| 当前 OWLX 词典 | 读音键仍来自拼音数据；新增成熟表码方案时必须绑定独立词典资产和许可清单 |

## 验证与回滚

单元测试验证 `NI'HAO` 在精确编码方案中规范化为 `ni'hao` 并精确查词，同时 `nh` 不触发全拼缩写。Core 配置合约验证运行中切换方案后缓存隔离和候选行为立即变化。回滚时移除 v13 字段和精确编码解析器即可；旧版仍可读取此前 v1～v12 配置备份。
