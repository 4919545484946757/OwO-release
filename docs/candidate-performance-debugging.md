# 安装版候选生成计时

入口：设置中心 → 调试与性能。无需开发版 CLI；该页和计时采集均包含在正常 Release 构建中。默认不采样、不联网、不上传。

## 使用

1. 确保 Core、ModelHost、设置中心及 TSF 为同一次构建。更新后重新打开测试应用，旧窗口可能仍加载旧 DLL。
2. 选择 1、5、10 或 30 分钟，点击“开始计时”，等待约 1 秒。
3. 切到记事本、WPS 或发生迟缓的应用，输入一组固定拼音，测试连续输入、翻页和展开。不要改变两台设备间的词库、学习状态、页长、纠错、分区及模型配置。
4. 返回调试页。页面在设置中心处于前台时每 2 秒增量读取记录，退到后台或离开页面则停止汇总刷新（原生采集继续），减少低配设备上的测量干扰。也可“刷新结果”；展开“阶段耗时”查看全局分位数，点击请求查看明细和事件时间线。
5. 停止计时，等待约 1 秒再刷新，导出 JSON 报告。导出不会上传；关闭设置中心或到期自动停止采集。

建议分开采样基础排序和智能排序，区分首轮冷请求、重复热请求、快速连续输入及翻页。逐键输入会正常淘汰旧请求，不能将被淘汰请求当作超时或成功延迟样本。

## 统计口径

| 项目 | 含义 |
| --- | --- |
| 首批可用 | TSF `OnKeyDown` 起点到首次非空候选快照的 UI 更新提交；鼠标或其他非按键触发从请求入队开始 |
| 精化完成 | 到不再等待纠错/基础候选精化的快照提交；不包括尚未应用的智能排序 |
| 模型应用 | 到 TSF 实际接受并提交模型更新；模型已经算完但没有应用，不会伪造这个值 |
| TSF 工作者排队 | 请求入队到发出基础/精化 IPC；同请求多轮累计 |
| 预编辑同步/即时预览更新 | 请求入队后同步输入位置预编辑、立即重绘拼音预览的 UI 工作；与后台 Core 工作可能重叠 |
| 基础/精化 IPC | TSF 到 Core 的往返，包含连接、串行服务等待和 Core 工作 |
| Core 接收前等待 | 发出 IPC 到 Core 解码后接收点，包含请求编码、连接、传输、调度与串行服务排队 |
| 响应返回等待 | Core 准备完成到 TSF 收到，包含响应编码、写出、传输和调度 |
| Core 处理 | 收到并解码请求后到响应准备完成，包含配置/词库刷新、符号附加行等；不含后续响应编码/写出 |
| 解析、召回、查询、排序 | 复用生产链路的阶段计时；查询/排序嵌套在候选生成内，分割/纠错嵌套在解析内 |
| Core 布局/分页 | 生成结束后到当前页面和模型候选池准备完成；不是纯比较排序时间 |
| 传输/服务等待残差 | IPC 往返减去已观测 Core 处理、编码和写出；还含连接、进程调度和服务排队，不能当作纯管道成本 |
| UI 消息调度 | 候选转换完成准备投递到 UI 接收之间的间隔 |
| 界面更新/绘制提交 | 调用候选窗口更新的 CPU 时间；包括布局/材质/绘制提交，不等于 GPU 完成或屏幕实际显示时间 |
| ModelHost 评分 | 模型后端 `rank()` 的执行时间，与 Core→ModelHost 往返和 TSF 等待模型更新分开记录 |
| 模型候选元数据准备 | Core 布局中的子阶段；未实际提交模型任务的路径跳过此项，计为实际零工作量，不与父阶段重复相加 |
| 模型工作队列 | Core 排队到模型任务实际开始；尚未开始或被替换的任务不伪造等待时间 |

P50/P95 使用 nearest-rank。首批、精化、模型应用各自按实际完成的有效样本统计；失败/超时与淘汰单独标记。阶段分位数以每请求累计工作量为样本，包含已发生的失败/淘汰阶段。不同阶段相互嵌套，不要相加重建总延迟。

统计以请求 ID 为单位：快速轮次与精化共用一个 ID；自动错误重试会成为新请求，单独显示，不把重试前的失败等待伪装为一次成功请求的内部阶段。

缺失阶段为未知（`—`），不是零。缓存命中时实际未执行解析/召回可以为零。仅有 Core 记录、没有 TSF 入队事件的片段保留在报告事件里，不进入端到端统计。

当前覆盖内置拼音/精确编码候选主链路及相关符号行、分页、精化和本地智能排序。Agent、选区大模型 API、插件独立输入方案不属于这个计时视图。采集开始前已完成的启动/词典加载不能追溯；冷启动等待只能从请求等待等已观测阶段判断，不能凭残差断言具体原因。

## 如何定位

- 排队高：检查 TSF 工作者是否忙于上一请求/反馈，或连续输入导致积压。
- IPC 高而 Core 低：先查连接、其他宿主占用、串行服务排队和安全软件；不是立即扩大算法预算。
- 准备高：检查导入词库更新、索引构建和配置刷新。
- 解析/纠错高：对比分割路径、输入长度和纠错开关。
- 召回/查询高：对比词库数量、缩写/混拼及缓存命中。
- Core 布局高：检查候选池规模、分区与分页编排。
- 模型高：分别比较 ModelHost 评分、模型 IPC、TSF 更新等待。若显示“模型未应用”，不能将模型完成时间当成用户已看见的排序时间。
- UI 调度高：宿主 UI 线程可能繁忙。
- 绘制提交高：对比材质插件、展开状态、候选长度及应用环境。

这些是定位线索，不是单个数值就能确诊的因果关系。记录覆盖缺失、事件丢弃或容量告警出现时，应先缩短采样并补齐组件版本。

## 隐私、容量与清理

- 只写固定事件名及数值：请求 ID、PID、输入长度、页号、配置状态、缓存/取消状态和耗时。不写原文、候选文字、前后文、窗口标题、可执行文件路径、API 密钥或应用文本。
- 本地目录为 `%LOCALAPPDATA%\OwO\InputMethod\diagnostics`。每会话随机 ID、每进程独立 JSONL，避免多个 TSF 宿主相互覆盖。
- UI 线程只入有界内存队列；现有工作线程批量写入，不创建逐按键线程，不改变候选 IPC 或公开插件协议。
- 每进程文件最多 8 MiB；队列最多 1024 条；界面每次读取最多 2 MiB、每会话最多 50,000 条事件。达到容量或权限不足会丢弃诊断事件，不阻塞正常候选；应结合覆盖、丢弃计数和容量提示判断报告完整性。
- AppContainer、受限完整性宿主或 AppData 重定向可能无法写入共享目录；不降低 ACL 或突破沙箱。页面会提示缺少 TSF/Core 记录，不会补造耗时。
- 采样绑定设置中心 PID 和进程创建时间：关闭、崩溃或重启后，旧标记不能重新激活采集；采样时限作为额外上限。受限宿主无法验证控制进程时拒绝采样，不放宽权限。记录不会自动删除；“清除此轮记录”只删除该会话文件，需确认，不能从应用恢复，不影响学习/词库/插件数据。
- 导出包含 OS/架构、逻辑处理器数量、进程可用内存上限和设置中心版本。请求 ID 导出为字符串，避免 JavaScript 64 位整数精度丢失。未自动收集 CPU 型号、用户名或设备标识；比较设备时可另行提供硬件说明。
- 调试本身有采样、缓冲及文件 I/O 开销；不要把开着调试时的测量值当作零开销基准。
